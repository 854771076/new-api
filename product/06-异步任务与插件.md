# 06 · 异步任务与插件

> [← 返回目录](README.md)

---

## 1. 定位

图片生成、视频生成、音乐生成、离线语音转写——这些能力有一个共同点：**耗时远超普通 API 请求**。

New API 用**任务插件**机制承载这类能力。业务方不需要理解各厂商协议差异，统一按"提交 → 轮询 → 取产物"的异步范式使用。

---

## 2. 为什么需要插件机制

| 传统做法的痛点 | 插件机制的解法 |
| --- | --- |
| 每接一家视频厂商就要写一套接入代码 | 每个厂商写一个插件，主机统一调度 |
| 厂商协议差异大（提交、轮询、下载各不相同） | 主机定义统一任务生命周期，插件只做协议翻译 |
| 异步任务难以计费 | 插件声明用量事实，主机统一结算 |
| 长耗时请求占用连接 | 任务在后台执行，客户端只轮询状态 |
| 产物格式各异（URL / base64 / 文件） | 主机统一为产物（artifact）模型 |

---

## 3. 任务生命周期

```
① 提交      POST /v1/tasks/{pluginKey}  或协议专用端点
              ↓  拿到 task_id
② 执行      后台轮询上游，绑定渠道，受并发约束
              ↓
③ 状态      GET /v1/tasks/{taskId}  → 状态 + 进度 + 产物
              ↓
④ 产物      GET /v1/tasks/{taskId}/artifacts
              GET /v1/tasks/{taskId}/artifacts/{artifactKey}/content
              ↓
⑤ 结算      插件上报用量事实，主机按计费表达式结算
```

任务状态通常是「排队中 → 进行中 → 成功 / 失败」，具体状态集合由插件声明。

---

## 4. 宿主协议

插件不直接注册 HTTP 路由，而是**声明自己要实现哪个宿主协议**。主机据此注册路由并调度。

### 4.1 四种宿主协议

| 协议 | 端点 | 模式 | 适用 |
| --- | --- | --- | --- |
| `openai_responses` | `POST /v1/responses`、`GET /v1/responses/{response_id}` | stream / sync / background | 通用异步任务 |
| `openai_video` | `POST /v1/videos`、`GET /v1/videos/{task_id}`、`GET`/`HEAD /v1/videos/{task_id}/content` | create + retrieve + content | 视频生成 |
| `openai_audio` | `POST /v1/audio/transcriptions/tasks`、`GET /v1/audio/transcriptions/tasks/{task_id}` | 仅异步 | 音频转写 |
| `openai_image` | `POST /v1/images/generations`、`POST /v1/images/edits` | 仅同步 | 图片生成 |

### 4.2 三种请求模式

| 模式 | 钩子 | 行为 |
| --- | --- | --- |
| `stream` | `renderEvents` | 流式返回事件 |
| `sync` | `renderFinal` | 阻塞到终态后返回最终结果 |
| `background` | `renderFinal` | 立即返回任务句柄，后台执行 |

**协议与模式的组合决定语义**：

- `openai_audio` 只有 create 与 retrieve，天然异步——提交即建任务，retrieve 渲染已存结果
- `openai_image` 只有 create 没有 retrieve：请求会建任务，宿主等到任务终态后直接返回渲染好的图片响应
- `openai_video` 与 `openai_responses` 同时支持同步与后台

### 4.3 未声明协议的模型

若请求的模型没有插件声明对应协议，会**回落到常规 Relay 路径**，而不是报错。这让同一端点既能接普通上游模型，也能接插件模型。

## 5. 插件组成

### 5.1 Manifest

每个插件有一个 manifest，声明：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `apiVersion` | 是 | 插件 API 版本，如 `1` |
| `key` | 是 | 插件唯一标识，全局唯一 |
| `name` | 是 | 展示名 |
| `version` | 是 | 插件版本号 |
| `author` | 是 | 作者信息，形状为 `{ name: "..." }` |
| `models` | 是 | 插件能处理的模型列表 |
| `fetchMode` | 是 | 取数模式，如 `per_task`（每任务一次拉取） |
| `description` | 否 | 描述文本，若提供必须用多语言对象且至少含 `en` 键 |
| `channelTypes` | 否 | 插件可绑定的渠道类型 ID 列表 |
| `icon` | 否 | 图标标识 |
| `usageSchema` | 否 | 用量字段定义（用于计费） |
| `usageProfiles[]` | 否 | 分档用量定义，按模型选择适用的 schema 字段 |
| `usageExamples` | 否 | 仅用于展示的定价示例，不影响计费 |

### 5.2 LocalizedText

描述性文本若提供，可以是**纯字符串**（等价于只提供 `en`），也可以是 `LocalizedText` 多语言对象；使用对象形式时至少必须包含 `en` 键。`meta.description` 与各字段的 `description` 在 Schema 中均为**可选**，但插件元数据会显示在管理台的插件列表与模型选择器里，因此实际提交时应补齐。

各语言的措辞必须等价、简短，不含数字价格与结尾标点。

### 5.3 宿主能力（Host utilities）

插件运行在 JavaScript 运行时（Sobek）中，宿主提供以下工具：

| 类别 | 可用能力 |
| --- | --- |
| **时间与随机** | `utils.unixNow`、`utils.uuid` |
| **编码与哈希** | `utils.base64`、`utils.base64URL`、`utils.base64URLDecode`、`utils.hmacSHA256`、`utils.hmacSHA1Base64` |
| **签名** | `utils.jwtSignHS256`、`utils.volcSignV4`（火山引擎 V4 签名） |
| **能力探测** | `utils.hasCapability` |
| **日志** | `console.log` |
| **JSON** | `utils.json.clone` |

> **注意**：宿主**不提供**通用的 HTTP 请求、产物存储或用量上报工具。调上游 API 通过插件的 request descriptor（`url` / `method` / `headers` / `body`）声明；产物落盘与用量采集由宿主在 `extractUsage*` 与渲染钩子中完成，插件不直接调用这些能力。

### 5.4 原生接口（Native surface）与 Origin Tasks

这是两个不同概念，容易混淆：

**原生接口（Native surface）**：插件可以声明厂商自己的非 OpenAI 形态 API，通过 `native.createJob` / `jobCreated` / `jobStatus` / `error` 呈现。宿主负责鉴权、归属校验、落库，并替换掉厂商私有的 task-id 字段。

**Origin Tasks（跨任务引用）**：解码钩子把厂商的草稿 / 续接 / 素材引用归一化为 `originTaskIds`（公开网关任务 ID）。宿主校验归属（要求同一插件平台且同一渠道），并注入 `ctx.originTasks`。**渲染器与 presenter 不会收到 `originTasks`。**

### 5.5 驱动钩子（Driver hooks）

用于产物处理的钩子：

| 钩子 | 用途 |
| --- | --- |
| `listArtifacts` | 列出任务产物 |
| `buildContentRequest` | 构造产物下载请求 |

### 5.6 取数模式（fetchMode）

`fetchMode` 是必填字段，声明插件如何取上游数据。绝大多数内置插件使用 `per_task`（每个任务提交后独立拉取一次上游结果），`sunoapi` 等则使用 `batch`（一次请求批量查询多个任务）。

## 6. 计费

### 6.1 用量事实

插件在任务完成时上报**实测用量事实**，主机据此结算：

| 插件类型 | 上报维度 |
| --- | --- |
| 视频 | 生成秒数 |
| 图片 | 生成张数 |
| 音乐 | 时长 |
| 语音转写 | 音频秒数 |

**计费以完成时的实测值为准**，而非请求时的预估。这是异步任务计费的关键——预估只用于预扣。

### 6.2 `usageSchema` 的描述规范

`usageSchema` 与 `usageProfiles[].schema` 中的数值型字段，其 `description` **必须命名计费主体与单价**，因为它会作为价格输入项显示在界面上：

| 字段 | 类型 | 必传 | 说明 |
| --- | --- | --- | --- |
| `image_count` | `number` | — | 图片生成单价（`unit: "count"`） |
| `seconds` | `number` | — | 视频生成单价（`unit: "second"`） |

字段值本身仍是**用量数量**，不是价格。

单位放在 `unit` 字段，取值只能是 `second` / `count` / `token` / `credit`。协议限制、用量来源、默认值、估算与结算细节放在代码注释或技术文档里——描述文本要简短、各语言等价、不含数字价格与结尾标点。

### 6.3 插件计费表达式

插件可在 `plugin_billing_expr` 中声明自己的计费表达式，按插件上报的用量事实结算。

## 7. 内置插件

| 插件 | 能力 |
| --- | --- |
| `alibaba` | 通义万相 + Qwen-Image / Qwen-Image-Edit / Z-Image（文生图、图生图、视频） |
| `doubao` | 豆包 Seedance 视频 |
| `google` | Veo（Gemini API） |
| `vertex-ai` | Veo（Vertex AI） |
| `hailuo` | MiniMax 海螺视频 |
| `jimeng` | 即梦图像 |
| `kling` | 可灵视频 |
| `sora` | Sora 视频 |
| `vidu` | Vidu 视频 |
| `sunoapi` | Suno 音乐 |
| `xfyun-asr` | 讯飞 IFASR 离线转写 |

### 7.1 各插件的计费维度不同

例如 `hailuo` 插件中，**只有 MiniMax-H3 模型对输入素材计费**（`input_images`、`input_video_seconds`）——不同模型族的计费维度不一样。

因此插件用**一份 `usageSchema` 加 `usageProfiles[]`** 按模型选择适用字段，而不是给每个模型各写一份 schema。

### 7.2 多模型族支持

`doubao` 插件的分辨率支持范围来自 Ark 模型列表（而非价格表），每个模型可用的分辨率、是否接受参考视频输入，各不相同。插件会镜像各模型的官方支持列表。

## 8. 轮询契约

轮询由**主机**驱动，插件提供查询/解析钩子、终态判定与进度上报。轮询间隔、超时与失败阈值由**主机配置**决定，不存在按插件单独配置轮询间隔的机制。

| 责任方 | 内容 |
| --- | --- |
| **插件提供** | 查询上游的钩子、解析响应、识别终态状态、上报进度 |
| **主机配置** | 轮询间隔、单次请求与单钩子超时、失败阈值（`TASK_POLL_MAX_FAILURES`）、整体截止时间（`TASK_TIMEOUT_MINUTES`） |

---

## 9. 轮询期的错误分类

宿主在**信任解析结果之前**先按 HTTP 状态分类，这是插件作者必须知道的实际契约：

| 上游状态码 | 宿主行为 |
| --- | --- |
| 2xx | 调用解析钩子（`parseTaskResult`） |
| 404 / 410 | 任务**立即判定失败**并触发退款 |
| 401 / 403 | 任务状态不变，累加 `PollFailures` 并告警；**渠道不会被自动禁用** |
| 429 / 5xx / 传输错误 | 累加 `PollFailures` |
| 其他 4xx | 仍调用解析钩子；结果若仍为非终态，视为无法识别并累加 `PollFailures` |

累计失败达到 `TASK_POLL_MAX_FAILURES`（默认 20）时，任务转为失败并触发退款链路。

插件返回的**面向用户的错误消息**可由 `native.error` presenter 改写原生错误体；错误码与可重试性由宿主按上述规则判定，不由插件声明。错误信息中的凭据类内容会被脱敏。

## 10. 持久化数据

插件可使用宿主的持久化能力存储任务相关数据。宿主的任务产物存储（task artifact store）提供：

| 能力 | 说明 |
| --- | --- |
| 产物存储 | 大文件不经过数据库 |
| 内容获取 | 统一的产物下载入口 |
| 清理 | 产物生命周期管理 |

---

## 11. 立即完成与提交流

部分能力可以**立即返回**而不走完整异步流程（如某些图片生成同步完成）。插件可声明此类行为，宿主据此直接渲染结果、**跳过轮询**。

但**任务记录仍会落库**——用于计费与任务日志；仅丢弃 `task.data`（`openai_image` 场景下还会丢弃快照）。

## 12. 开发插件

### 12.1 目录结构

```
plugins/tasks/<plugin-name>/
  plugin.js        # 插件主体
```

### 12.2 最小插件骨架

宿主加载的是 `meta` 导出（不是 `manifest`），且 `apiVersion`、`key`、`name`、`version`、`author`、`models`、`fetchMode` 为 Schema 必填项：

```javascript
export const meta = {
  apiVersion: 1,
  key: 'my-plugin',
  name: 'My Plugin',
  version: '1.0.0',
  author: { name: 'Your Name' },
  models: ['my-model'],
  fetchMode: 'per_task',
  usageSchema: {
    seconds: {
      type: 'number',
      unit: 'second',
      description: { en: 'Video generation unit price', zh: '视频生成单价' },
    },
  },
}

// openai_video 的 content 操作需要这两个驱动钩子，缺失会在加载时被拒绝
export const listArtifacts = (ctx) => ctx.row?.data?.artifacts ?? []

export const buildContentRequest = (ctx) => ({
  url: `${ctx.baseUrl}/videos/${ctx.taskId}/content`,
  method: ctx.method,
  headers: ctx.headers,
})

export const protocols = {
  openai_video: {
    decodeRequest(ctx) { return { kind: 'submit', model: ctx.model }; },
    render(ctx) { return ctx.task; },
  },
}
```

**合法的 `unit` 值**只有四个：`second`、`count`、`token`、`credit`。写成 `seconds` 会被拒绝。

计费数值字段的 `description` 必须命名**计费主体 + 单价**（如 `Video generation unit price` / `视频生成单价`），单位放 `unit` 字段，字段值仍是用量数量。

### 12.3 开发前必读

| 文档 | 用途 |
| --- | --- |
| `docs/plugin-api/v1.md` | 完整 API 规范，含描述撰写与翻译约定 |
| `docs/plugin-api/v1.schema.json` | Manifest 的 JSON Schema |
| `docs/plugin-api/v1.d.ts` | TypeScript 类型定义 |

改插件契约时，`.md`、`.schema.json`、`.d.ts` 三者需保持一致。

### 12.4 契约一致性检查

插件编译成功、Schema 校验通过、测试通过——这些都**不能**验证描述文案是否合规。规范要求：

- 数值型 `usageSchema` / `usageProfiles[].schema` 字段的 `description` 必须命名**计费主体 + 单价**
- 单位必须在 `unit` 字段
- 描述简短、各语言等价、无数字价格、无结尾标点
- 协议限制、用量来源、默认值、估算与结算细节写进代码注释或技术文档

**元数据措辞需要显式复核**——这是撰写要求，不是工具能自动检查的。
