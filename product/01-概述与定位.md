# 01 · 概述与定位

> [← 返回目录](README.md)

---

## 1. 一句话定义

New API 是一套面向应用、Agent 和团队的**自托管 AI 网关**。连接上游模型服务，向客户端暴露一致的 API，并把路由、访问、用量与成本集中管理在一处。

---

## 2. 它解决的问题

### 2.1 四个真实痛点

组织在引入多个模型供应商时，会同时遇到四类成本。New API 逐项对应：

| 痛点 | 具体表现 | New API 的做法 |
| --- | --- | --- |
| **接入成本** | 每接一家厂商就要改一版客户端代码，SDK 版本、协议细节、错误格式各不相同 | 统一暴露 OpenAI 兼容协议，客户端只改 `model` 字段 |
| **成本不可见** | 不知道哪个部门、哪个应用、哪个模型花了多少钱，无法归集 | 每次调用记录用量与费用，可按用户、令牌、分组、模型、渠道多维归集 |
| **稳定性不可控** | 单个上游抖动就影响业务；上游限流直接失败；没有故障转移 | 渠道池 + 优先级权重 + 重试 + 自动禁用 + 渠道亲和 |
| **账号难管理** | 上游账号、密钥、额度散落各处，谁在用、还剩多少说不清 | 渠道统一纳管：多 Key 池、余额监控、自动禁用、模型同步 |

### 2.2 典型收益

| 收益 | 说明 |
| --- | --- |
| 客户端零改造 | 换供应商不改调用代码，只改模型名 |
| 供应商可替换 | 同一模型配多条渠道，可随时切换、灰度、按权重分流 |
| 成本可归集 | 用量日志天然带完整归因维度 |
| 权限可分发 | 令牌按分组授权，分组决定可见模型与计费倍率 |
| 私有可控 | 网关与用量数据可自托管于内网；请求内容仍会转发至所配置的上游供应商，数据边界需结合上游部署形态评估 |

---

## 3. 目标用户

| 角色 | 用 New API 做什么 |
| --- | --- |
| **平台团队** | 统一纳管公司的模型访问入口，做配额、路由、审计 |
| **业务团队** | 拿一个 API Key 就能用上多个模型，不用申请各家账号 |
| **运维 / SRE** | 看渠道健康度、用量峰值、失败率，做容量与故障处置 |
| **财务 / 成本管理** | 通过用户 / 令牌 / 分组映射部门或项目，再按模型拆账 |

---

## 4. 核心价值主张

> **模型访问是分布式的，成本与治理应该是集中的。**

New API 把"从谁那里调用"这个复杂度留在网关内部，把"要什么能力"这个简单问题交给客户端。这一层同时承载了三件事：

1. **协议统一** —— 四套主流文本协议互转，客户端不必为每家厂商写适配
2. **资源调度** —— 多渠道、多 Key 的选路、重试、降级、故障隔离
3. **计量计费** —— 谁用了、用了多少、该付多少，全链路可追溯

---

## 5. 与常见方案的差异

| 维度 | 直连上游 | 通用 API 网关 | New API |
| --- | --- | --- | --- |
| 模型协议适配 | 逐家适配 | 多数只做 HTTP 转发 | OpenAI / Anthropic / Gemini / Responses 四套协议互转 |
| 计量归集 | 无 | 按请求数计费 | 按 token / 图片张数 / 音频秒数 / 任务时长，按模型定价 |
| 用量归属 | 无 | 按 API Key | 用户、令牌、分组、模型、渠道多维 |
| 任务型能力 | 需自行开发 | 通常不支持 | JS 插件机制扩展异步任务 |
| 权限模型 | 各自账号 | 简单 Key | 用户 / 角色 / 分组 / 令牌 / 细粒度策略 |
| 私有化 | 需自建 | 多不支持 | 一条 docker compose 起 |

**差异的本质**：New API 不是"转发器 + 计数器"，而是把模型调用当成一个**需要计量、调度和审计的业务系统**来设计。

---

## 6. 适用场景

| 场景 | 说明 |
| --- | --- |
| 团队共享模型访问 | 一份服务端多个客户端用，按令牌分发 |
| 私有多模型服务 | 内部署一套，服务多个业务线 |
| 多供应商成本归集 | 需要按部门、项目核算 AI 支出的组织 |
| 上游统一收口 | 公司只有一份上游合约，需要内部二次分配 |
| 供应商切换演练 | 关键模型配多渠道，可控灰度切换 |
| AI 应用开发底座 | Agent / 应用需要一个稳定的模型入口 |

---

## 7. 不适用场景

这一节和上一节同样重要。

| 不适用 | 原因 |
| --- | --- |
| **面向公网转售 / API 分销** | 产品明确声明仅用于合法授权场景。转售需自行完成备案、许可、内容安全、实名验证、日志留存、税务、支付与上游授权等全部义务 |
| **需要按租户分片的 SaaS 多租户** | 当前架构无分片键概念，属于 out of scope |
| **要求 active-active 多活** | 不在范围内（架构取舍见 [08-部署与运维](08-部署与运维.md)） |
| **Redis Cluster 部署** | 已明确排除，高可用走 Sentinel 路线 |
| **替代厂商原生能力** | 网关只做协议转换与调度，不提供厂商独有的高级能力（如某家的私有检索增强接口） |

## 8. 产品边界总览

```
                    ┌───────────────────────────────────────┐
   客户端应用  ────▶│  统一 API 层                          │
   (OpenAI 兼容)     │  OpenAI / Anthropic / Gemini /        │
                     │  Responses 四套协议                    │
                     └──────────────────┬────────────────────┘
                                        │
                    ┌──────────────────▼────────────────────┐
                    │  治理层                                │
                    │  路由调度 │ 访问控制 │ 计量计费 │ 审计  │
                    └──────────────────┬────────────────────┘
                                        │
                    ┌──────────────────▼────────────────────┐
                    │  上游层（40+ 供应商，59 种渠道类型）    │
                    └───────────────────────────────────────┘
```

**New API 负责**：协议转换、渠道调度、访问控制、用量计量、计费结算、审计留痕、任务扩展。

**New API 不负责**：上游模型本身的推理质量与训练数据、上游账号的申请与合规、客户端应用本身的业务逻辑。

## 9. 一次请求的完整链路

理解这条链路，是理解整个产品设计取舍的前提。

```
① 客户端携带 Bearer 令牌发起请求
        ↓
② 认证：校验令牌有效性、过期、模型白名单
        ↓
③ 访问控制：检查用户分组、模型权限、请求策略
        ↓
④ 额度预检：按计费表达式预估费用，预扣配额
        ↓
⑤ 选路：按模型查能力集合 → 优先级 → 有效权重 → 取并发槽位
        ↓
⑥ 转发：转换为上游协议 → 调用上游 → 转换响应（含流式）
        ↓
⑦ 结算：按实际用量结算，与预扣额度多退少补（固定价 / 按张 / 按秒 / 任务计费等路径不依赖 token 用量）
        ↓
⑧ 落日志：用量、费用、渠道、耗时分段、错误码
```

每一步都对应管理台上的一个可观测面：**认证**看令牌，**访问控制**看分组与策略，**计费**看用量日志，**路由**看渠道健康度，**审计**看操作日志。
