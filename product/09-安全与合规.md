# 09 · 安全与合规

> [← 返回目录](README.md)

---

## 1. 定位

网关持有全部上游密钥，是组织 AI 支出的唯一收口——同时也是高价值攻击目标。本章说明产品的安全设计，以及**使用者必须自行承担的责任**。

---

## 2. 鉴权模型

### 2.1 两类主体

| 主体 | 凭证 | 入口 |
| --- | --- | --- |
| **业务调用方** | API 令牌（`sk-...`） | `/v1/*` |
| **管理操作方** | 短期 Access Token（Bearer）/ Refresh Cookie / 系统访问令牌（PAT） | `/api/*` |

面板鉴权采用短期 Access Token + HttpOnly Refresh Cookie（仅用于 `/api/user/auth/refresh`），加上 PAT。单独携带会话 Cookie 并不能认证 `/api/*` 请求。

管理面与数据面**权限分离**：业务令牌不能调用管理接口，管理会话不能当业务令牌用。

### 2.2 权限判定

详见 [04-用户与访问控制](04-用户与访问控制.md#22-角色体系)。核心规则：

- 超级用户角色短路允许
- 显式 `deny` 优先于 `allow`
- 未知权限默认拒绝

### 2.3 角色隔离

系统角色（用户属性）与授权角色（策略主体）分离：

| | 系统角色 | 授权角色 |
| --- | --- | --- |
| 决定 | 能进哪个界面、能调哪个接口 | 能对哪个资源执行哪个动作 |
| 载体 | 用户表的 role 字段 | `authz_roles` 表 + Casbin 策略 |
| 例子 | root / admin / 普通用户 | 自定义角色与用户级覆盖 |

## 3. 浏览器接口安全

### 3.1 会话签发限额与保留策略

系统对会话签发有数量与保留期限制，防止会话无限增长或长期不失效。

### 3.2 Refresh / Logout 的 Origin 校验

刷新与登出接口校验 `Origin` 头，防止跨站请求伪造（CSRF）：

- `SESSION_COOKIE_TRUSTED_URL` 配置了精确的 HTTPS origin 列表（逗号分隔，不带路径与通配符）
- Secure 模式下启用严格的刷新与登出来源检查
- 本地 HTTP 调试场景可留空

### 3.3 可信代理与 IP 限流

`TRUSTED_PROXIES` 指定受信任的反向代理 IP/CIDR（可设 `none`）。**必须按实际网络显式配置**——未配置时，客户端 IP 判定可能不准，导致 IP 限流失效或误伤。

---

## 4. Personal Access Token 调用契约

PAT 用于脚本化管理自身账户资源。其调用契约与 API 令牌不同：

| 差异 | API 令牌 | PAT |
| --- | --- | --- |
| 入口 | `/v1/*` | `/api/*` |
| 作用范围 | 调用模型 | 管理自身账户资源 |
| 权限来源 | 所属用户 | **与所属用户等权**（用户是管理员时，其 PAT 亦可调用管理接口） |

PAT 唯一的能力限制是**不能通过 PAT 管理浏览器登录会话**（PAT 请求不携带 SessionID）。除此之外它与所属用户的面板凭证权限等价，因此须与其他高权限凭证同等保管。

---

## 5. 临时鉴权与二次验证

敏感操作（改密码、改邮箱、绑定账号、删除账户等）支持临时鉴权流程：先用主凭证换取一次性临时凭证，再用它完成敏感操作。

这实现了**敏感操作的二次确认**，即使主凭证泄露，攻击者也无法直接完成高危操作。

---

## 6. 认证方式

| 方式 | 说明 |
| --- | --- |
| 密码 | 支持登录密码传输加密（`PASSWORD_LOGIN_ENCRYPTION_ENABLED`） |
| 邮箱验证 | 注册确认、密码找回、邮箱绑定 |
| TOTP 双因素 | 可强制启用；登录二次校验 |
| WebAuthn / Passkey | 抗钓鱼强认证，依赖 HTTPS 与域名配置 |
| OAuth / OIDC | 见下 |
| 会话管理 | 查看与主动注销登录会话 |

### 6.1 内置 OAuth 提供方

| 提供方 | 说明 |
| --- | --- |
| `discord` | Discord 登录 |
| `github` | GitHub 登录 |
| `telegram` | Telegram 登录（含 Bot 流程） |
| `linuxdo` | LINUX DO 登录 |
| `oidc` | 通用 OIDC |
| `wechat` | 微信登录（含绑定流程） |

此外内置 `generic` 通用 OAuth 提供方模板，管理员还可配置**自定义 OAuth 提供方**，接入企业自有身份系统。

### 6.2 账号绑定与解绑

第三方账号可与本地账号绑定，也可解绑。绑定与解绑都走临时鉴权流程，且进审计日志。

## 7. 限流与防护

### 7.1 关键操作限流

登录、注册、密码重置、邮箱验证、OAuth 回调等按类型分级限流，防止撞库与资源滥用。

### 7.2 模型请求限流

可按分组配置模型请求的限流规则：

| 参数 | 说明 |
| --- | --- |
| 启用开关 | `ModelRequestRateLimitEnabled`，默认关闭 |
| 时间窗口 | `ModelRequestRateLimitDurationMinutes`，默认 1 分钟 |
| 计数阈值 | `ModelRequestRateLimitCount` |
| 成功计数阈值 | `ModelRequestRateLimitSuccessCount`，默认 1000 |
| 分组规则 | `ModelRequestRateLimitGroup`，按分组分别配置 |

限流时长上限 24 小时；计数上限受 `MaxInt64 / 86400` 约束，避免溢出。

### 7.3 其他防护

| 措施 | 说明 |
| --- | --- |
| Turnstile 人机校验 | 关键入口可开启 |
| 匿名请求体上限 | 限制未认证请求体积 |
| 验证码防重放 | 邮箱验证码、登录验证码独立校验 |
| 渠道自动禁用 | 避免持续打到已知故障上游 |
| 错误信息不泄露内部实现 | 上游错误经网关转译，不直接透出内部细节 |

## 8. 密钥管理

| 场景 | 要求 |
| --- | --- |
| 上游密钥 | 存在渠道配置中，仅管理员可见；不出现在日志与错误信息里 |
| 会话密钥 | `SESSION_SECRET` 持久化随机值，全节点一致，不进版本库 |
| 加密密钥 | `CRYPTO_SECRET` 默认继承 `SESSION_SECRET`；共享 Redis 的节点必须一致 |
| 客户端密钥 | API 令牌的完整密钥**可被所属用户再次读取**（前端默认掩码显示，但提供复制完整密钥的能力）。应视同长期凭据保管，泄露后需立即删除重建 |

---

## 9. 数据保护

| 数据 | 保护 |
| --- | --- |
| 密码 | 哈希存储（算法可配），永不明文落库 |
| 验证码 | 短期有效，用后失效，不入日志 |
| 会话与令牌 | 审计与认证事件中排除 |
| 密钥类内容 | 日志脱敏且有界 |
| 用户行为数据 | 可独立配置日志库保留期 |

---

## 10. 审计

管理写操作全部进审计日志（见 [07](07-可观测与管理控制台.md#7-审计日志)）。**审计与认证事件排除**：密码、验证码、恢复码、私钥、可用的会话或认证令牌。

---

## 11. 隐私与合规

### 11.1 使用者责任

New API 是**工具**，不承担使用者的合规责任。使用者必须：

| 责任 | 说明 |
| --- | --- |
| 合法取得上游资源 | API 密钥、账号、模型服务与接口权限须合法获得 |
| 遵守上游条款 | 遵守各上游的服务条款 |
| 遵守适用法律 | 遵守所在辖区的法律法规 |
| 备案与许可 | 面向公众提供生成式 AI 服务时，需完成备案、许可等义务 |
| 内容安全 | 履行内容安全义务 |
| 实名验证 | 按辖区要求履行 |
| 日志留存 | 按辖区要求留存 |
| 税务与支付 | 按辖区要求处理 |
| 上游授权 | 获得上游的转售或再分发授权（如适用） |

### 11.2 公开提供服务的额外义务

若将本项目作为**公开的生成式 AI 服务或 API 转售服务**运营，需先完成：备案、许可、内容安全、实名验证、日志留存、税务、支付与上游授权等全部义务。

### 11.3 产品侧提供的合规支撑

| 能力 | 支撑的义务 |
| --- | --- |
| 完整用量与审计日志 | 日志留存、追溯 |
| 用户 / 分组 / 令牌维度归集 | 内部成本核算与审计 |
| 渠道密钥集中管理 | 上游凭据的受控保管 |
| 权限体系 | 最小权限与职责分离 |

## 12. 安全基线建议

部署到生产前建议逐项确认：

| 项 | 检查 |
| --- | --- |
| HTTPS | 控制台与 API 都在 HTTPS 之后 |
| `SESSION_SECRET` | 持久化随机值，非示例值，全节点一致 |
| `CRYPTO_SECRET` | 全节点一致（未显式设置时继承 `SESSION_SECRET`）；变更前需迁移已加密数据，否则历史密文（如渠道密钥）无法解密 |
| `SESSION_COOKIE_SECURE` | `true` |
| `SESSION_COOKIE_TRUSTED_URL` | 精确的公开 HTTPS origin |
| `TRUSTED_PROXIES` | 按实际网络显式配置，不留空 |
| 数据库密码 | 已替换示例值 |
| 管理员账号 | 强密码 + 已启用双因素或 Passkey |
| 上游密钥 | 仅在渠道配置中，未出现在其他位置 |
| 备份 | 数据库与数据目录已备份且演练过恢复 |
| 版本 | 固定版本号，不跟随 `latest` |
