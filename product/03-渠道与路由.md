# 03 · 渠道与路由

> [← 返回目录](README.md)

---

## 1. 定位

渠道（Channel）是 New API 的核心配置对象。一条渠道记录了"**从哪一家、用哪个密钥、能提供哪些模型、按什么规则参与调度**"，并承载这一路流量的健康状态、余额与用量。

路由层回答的问题只有一个：**这次请求应该交给哪条渠道？**

---

## 3. 渠道配置项

| 配置 | 说明 |
| --- | --- |
| **基础信息** | 名称、类型、状态、备注、标签（Tag） |
| **密钥** | 单 Key 或多 Key 池。多 Key 支持两种模式：随机（random）与轮询（polling），并记录每个 Key 的状态、禁用原因与禁用时间 |
| **模型列表** | 该渠道可提供的模型；支持从上游自动同步模型列表与元数据 |
| **模型映射** | 把请求的模型名改写为上游实际模型名——一个渠道可承接多个业务模型名 |
| **分组** | 渠道归属的用户组，决定哪些令牌能用它 |
| **优先级** | 数值越大越优先 |
| **权重** | 同优先级渠道间的分流比例 |
| **并发上限** | 渠道级并发限制，`0` 表示不限 |
| **参数覆写** | 固定改写请求参数（如强制 temperature、注入参数） |
| **请求头覆写** | 固定改写上游请求头 |
| **状态码映射** | 把上游状态码映射为网关对外语义 |
| **余额** | 上游账户余额与最后更新时间（美元计价） |
| **代理** | 该渠道的出站代理地址 |
| **自动禁用** | 上游连续失败时自动摘除，避免持续打到坏渠道 |

### 3.1 渠道状态

| 状态 | 含义 |
| --- | --- |
| 启用 | 正常参与调度 |
| 手动禁用 | 管理员手工关闭 |
| 自动禁用 | 因连续失败或所有 Key 不可用被系统摘除 |

自动禁用的渠道在条件恢复后可自动恢复；手动禁用不会。

### 3.2 标签与批量操作

渠道可打标签，并按标签批量操作：批量启用、批量禁用、批量改模型列表、批量改分组、批量改优先级与权重、批量改模型映射。

标签级禁用会同时取消"因所有 Key 不可用而自动禁用"的自动恢复——避免手动操作被自动逻辑覆盖。

## 4. 能力（Ability）模型

New API 用**能力**这个中间层解耦"请求的模型"与"能提供该模型的渠道"。

```
模型 M  ──→  能力集合 A(M)  ──→  候选渠道列表  ──→  调度选择
```

能力记录的是"渠道 × 模型"的组合及其状态（是否启用、优先级、权重）。渠道改模型列表或分组时，能力集合随之重建。

这个设计的价值：模型可以有多个候选渠道，每个渠道可以被多个模型复用，而权限、状态、权重都挂在能力上而不是渠道上。

---

## 5. 调度算法

一次请求的选路流程：

```
① 请求模型 M、用户分组 G
        ↓
② 查能力集合：所有满足 (M, G, 启用) 的能力
        ↓
③ 渠道亲和检查：若命中亲和规则，优先返回亲和渠道
        ↓
④ 按优先级分组：取最高优先级的候选
        ↓
⑤ 有效权重分流：同优先级内按 EWMA 动态有效权重分配
        ↓
⑥ 取并发槽位：渠道并发已满则换下一条
        ↓
⑦ 选定渠道，进入转发
```

### 5.1 优先级与权重

- **优先级**是**分层降级**：首次尝试只取最高优先级组内的渠道；**每次重试整体下移一层优先级**。因此 `retry_times ≥ 1` 时，即使最高优先级组内仍有健康渠道，重试也可能落到下一层——优先级与重试预算相互耦合。
- **权重**是组内软分流：按权重比例分配请求量。

### 5.2 动态有效权重（EWMA）

除静态权重外，系统用指数加权移动平均计算**有效权重**，让慢渠道自动少分流量：

| 参数 | 值 |
| --- | --- |
| 生效前提 | **仅对显式配置了并发上限（`concurrency_limit > 0`）的渠道生效**；未配置（`0`，不限流）的渠道乘数恒为 1.0，不参与 EWMA 计算 |
| 预热门槛 | ≥ 10 个样本 |
| 乘数钳制区间 | [0.2, 5.0]；当前公式实际落在 **[0.2, 2.0]**（5.0 是结构上不可达的钳制上限） |
| 因子构成 | 成功率因子（≤1）× 延迟因子（≤2）× 在途负载因子（≤1，依赖并发上限） |
| 重算间隔 | 10 秒（反震荡） |
| 过期数据 | > 5 分钟丢弃，自愈 |

路由健康状态有只读观测端点，可在控制台查看。

### 5.3 逐 attempt 槽位强制

并发限制是**按每次上游调用**强制，而不是按请求：

- 每次尝试占用一个并发槽位
- 槽位满时按排除集换渠道（且不回头重试原渠道）
- 全部候选渠道都饱和时，才对客户端返回 429

> **前提**：换渠道重试依赖运维把 `retry_times` 调到 **≥ 1**。默认 `retry_times = 0` 时，首个渠道并发饱和即直接对客户端返回 429，即使还有其他空闲候选渠道。

这保证了在混合流量的场景下，不会出现某个渠道被并发放大到压垮上游的情况。

## 6. 渠道亲和（Channel Affinity）

### 6.1 它解决什么问题

某些场景需要同一会话稳定落到同一渠道：

- **提示词缓存**：上游按前缀缓存，换渠道会缓存失效，命中率归零
- **长会话一致性**：Agent 多轮对话分布在不同渠道，上下文与计费口径不一致

渠道亲和让符合规则的请求固定命中同一条渠道。

### 6.2 匹配维度

每条亲和规则可配置：

| 维度 | 说明 |
| --- | --- |
| 模型正则 | 只对匹配模型名的请求生效 |
| 路径正则 | 只对匹配请求路径的请求生效 |
| User-Agent 包含 | 按客户端标识区分 |
| 键来源 | 从请求体（`gjson`，如 `prompt_cache_key`、`metadata.user_id`）、请求头（`request_header`）或上下文（`context_int` / `context_string`）提取亲和标识 |
| 值正则 | 对亲和标识本身做过滤 |
| TTL | 亲和关系的存活时间，规则未指定时用默认值（默认 3600 秒） |
| 会话模式 | `off` / `prefer` / `strict` / `inherit`，决定亲和失败后是否重试 |

缓存键可组合规则名、模型名、分组与亲和标识，控制亲和关系的粒度。

### 6.3 内置规则

系统预置了两条规则，直接对应主流 CLI 工具：

| 规则 | 匹配 | 键来源 | 效果 |
| --- | --- | --- | --- |
| `codex cli trace` | 模型 `^gpt-.*$`、路径 `/v1/responses` | `prompt_cache_key` | 保持上游提示词缓存命中 |
| `claude cli trace` | 模型 `^claude-.*$`、路径 `/v1/messages` | `metadata.user_id` | 保持 Claude 会话一致性 |

两条规则都带参数覆写模板，用于透传相应 CLI 工具的请求头。

### 6.4 其他可配置项

| 配置 | 说明 |
| --- | --- |
| `switch_on_success` | 请求成功后，把亲和关系更新到实际成功的渠道 |
| `keep_on_channel_disabled` | 渠道被禁用时是否保留亲和关系 |
| `max_entries` | 亲和缓存最大条目数（默认 100000） |
| `default_ttl_seconds` | 默认存活时间（默认 3600 秒） |

亲和缓存采用混合缓存：Redis + 进程内 LRU 热缓存。**Redis 未启用时**使用进程内 LRU；**Redis 运行期异常时**，亲和查询失败并按"无亲和"放行（fail-open），**不会回退到本地缓存**。

## 7. 重试与失败处理

### 7.1 重试决策

重试不是无条件重发。系统按错误类型判定是否值得换渠道重试：

| 错误类型 | 处理 |
| --- | --- |
| 上游 429 | 触发跨渠道补跳（见下） |
| 上游 5xx | 按策略换渠道重试 |
| 上游 4xx（业务错误） | 通常不重试，直接返回客户端 |
| 亲和渠道失败 | 按会话模式决定是否跳过重试（`strict` 模式下跳过） |

### 7.2 429 的特殊处理

上游 429 **不做单跳终结**。主机在 Relay 循环内按**四条件谓词**判定是否授予**恰好一次**跨渠道补跳：

1. 重试决策为 stop，且原因为 `attempt_budget_exhausted`（重试预算已耗尽）
2. 错误状态码为上游 429
3. 本次请求此前只尝试过 **1 个**不同渠道
4. 本请求尚未发放过补跳授权

授予补跳时的行为：换道对客户端无感，且不回头重试原渠道。

> 注意区分两类 429：
> - **上游 429 补跳后仍失败** —— 透传上游原始 429，**不附带** `Retry-After`
> - **渠道并发饱和** —— 由网关的终态错误渲染器写出，**附带** `Retry-After`

### 7.3 自动禁用

不存在渠道级的"连续失败计数"。判定是**逐次**的：开启自动禁用后，单次错误命中渠道级错误类型、自动禁用状态码或自动禁用关键词，渠道**立即**被禁用，避免请求持续打到已知故障的上游。并发饱和拒绝被显式排除，以免误伤。

恢复条件满足时可自动恢复。

### 7.4 多 Key 池故障剔除

单渠道挂多把密钥时，失效的 Key 会被单独标记禁用并记录原因，不影响该渠道的其他 Key。**所有 Key 都不可用**时，该渠道才进入禁用状态。

## 8. 上游模型同步

渠道可从上游自动拉取模型列表与元数据，包括：

- 该渠道实际支持的模型
- 模型上下文长度等元数据
- 上游返回的模型变更

同步能力可按渠道类型启用（仅部分渠道类型支持拉取）。这减少了手工维护模型列表的成本，也让"新模型上线"能被及时发现。

## 9. 边界与注意事项

| 事项 | 说明 |
| --- | --- |
| 转换非无损 | 协议转换后部分厂商特有字段可能丢失，详见 [02](02-能力总览.md#15-关于协议转换的重要说明) |
| 模型名写错 | 无可用渠道时返回 `model_not_found`（503）；渠道侧映射缺失属另一类错误（`channel:model_mapped_error`），未配置映射时模型名原样透传、错误来自上游。可先看错误码区分，再结合上游实际收到的模型名排查 |
| 亲和与切换冲突 | 亲和生效时流量不会按权重重新分配，需要权衡缓存命中与负载均衡 |
| 并发上限为 0 | 表示不限流，不是"禁止使用" |
| 渠道禁用不影响在途任务 | 已绑定的进行中任务独立完成 |
