# 07 · 可观测与管理控制台

> [← 返回目录](README.md)

---

## 1. 定位

可观测回答：**谁调了什么、走了哪个上游、花了多少钱、为什么失败**。

New API 的可观测能力分三层：**消费日志**（每请求一条）、**统计看板**（聚合视图）、**审计日志**（管理操作）。三层共用一套数据底座。

---

## 2. 消费日志

### 2.1 记录字段

| 字段 | 含义 |
| --- | --- |
| `user_id` / `username` | 调用主体 |
| `token_id` / `token_name` | 使用的令牌 |
| `model_name` | 请求的模型 |
| `channel` / `channel_name` | 实际命中的上游渠道 |
| `group` | 使用的分组 |
| `ip` | 来源 IP |
| `quota` | 本次扣除的额度 |
| `prompt_tokens` | 输入 token |
| `completion_tokens` | 输出 token |
| `use_time` | 耗时 |
| `is_stream` | 是否流式 |
| `request_id` | 网关侧请求 ID |
| `upstream_request_id` | 上游返回的请求 ID（便于对账上游账单） |
| `content` | 文本描述 |
| `other` | 扩展 JSON（分项用量、耗时分段、错误码、管理员信息等） |
| `created_at` / `type` | 时间与日志类型 |

`other` 字段是扩展信息的容器，按需承载：

| 内容 | 说明 |
| --- | --- |
| 缓存 token 分项 | 缓存读取 / 创建的 token 数 |
| 图片 / 音频分项 | 分维度用量 |
| 工具调用次数 | Responses 协议的内置工具调用 |
| 错误码 | 细粒度失败原因 |
| `admin_info` | 管理员专属信息（配额截断标记、渠道亲和详情、**耗时分段**等） |

> `admin_info` 嵌套是有意设计：管理台自动可见，普通用户侧自动剥离，不需要额外配置。**耗时分段也在其中，普通用户在日志中看不到这些分段。**

### 2.2 日志类型

| 类型 | 值 | 说明 |
| --- | --- | --- |
| Unknown | 0 | 未分类 |
| Topup | 1 | 充值 |
| Consume | 2 | 消费 |
| Manage | 3 | 管理操作 |
| System | 4 | 系统事件 |
| Error | 5 | 错误 |
| Refund | 6 | 退款 |
| Login | 7 | 登录 |

> 类型值使用常量而非 iota，避免后续新增类型时改变已有值。

### 2.3 索引设计

日志表按查询维度建索引：

| 索引 | 支撑的查询 |
| --- | --- |
| `idx_created_at_id` | 时间范围 + 分页 |
| `idx_user_id_id` | 按用户查 |
| `idx_created_at_type` | 按类型 + 时间查 |
| `index_username_model_name` | 按用户名 + 模型聚合 |
| `idx_logs_request_id` | 按请求 ID 追踪 |
| `idx_logs_upstream_request_id` | 按上游请求 ID 对账 |
| `channel` / `group` / `ip` / `token_id` | 各维度过滤 |

### 2.4 请求 ID 追踪

每条日志带 `request_id`（网关生成）与 `upstream_request_id`（上游返回）。两者都可用于：

- 客户端报障时按 request_id 定位
- 与上游账单对账时按 upstream_request_id 反查

## 3. 耗时分段

请求耗时不只有一个总时长。系统采集的分段快照（`RequestTiming.Snapshot()`）包含 11 个固定键：

| 分段 | 含义 |
| --- | --- |
| 排队等待 | 在网关内的等待（并发闸门 + 等待队列） |
| 选渠道 | 选择上游渠道的耗时（多次 attempt 累加） |
| 上游响应头 | 发出请求到收到上游响应头 |
| 上游响应体 | 读取完整响应体（非流式路径） |
| 上游首包 | 到第一个流式数据块 |
| 上游流持续 | 流式传输持续时长 |
| 结算 | 计费结算耗时 |
| 尝试次数 | 本次请求尝试上游的次数 |
| 三个超时阈值 | 上游响应头超时、流式超时、转发总超时的配置值 |

各分段在日志列表与详情弹窗呈现，是定位"慢"在哪一环的主要依据。总耗时与各分段之和不完全相等时，看板会展示差额，便于发现无法解释的耗时。

## 4. 错误可归因

上游失败按**细粒度错误码**分类留痕，而不是笼统的"请求失败"。系统日志按任务码类别记录，**超时类不再静默**。

| 改进前 | 改进后 |
| --- | --- |
| 粗码 `do_request_failed` | 按 relaykit 细粒度错误码分类 |
| 系统日志靠文本匹配"post/dial/http" | 按任务码类别留痕，超时类显式记录 |
| 上游传输失败无细分 | 拆分为细粒度错误码 |

日志留痕**脱敏且有界**——凭据类内容不会进日志，体积有上限。

## 5. 统计看板

### 5.1 数据接口

`/api/data` 提供聚合统计，配合 `/api/log` 做明细下钻。

### 5.2 用量统计

| 维度 | 说明 |
| --- | --- |
| 按用户 | 谁的用量最多 |
| 按令牌 | 哪个应用消耗最多 |
| 按模型 | 哪些模型成本高 |
| 按渠道 | 哪些上游花钱多 |
| 按分组 | 内部转移定价的成本分布 |
| 按时间 | 用量趋势与周期性 |

### 5.3 用量数据模型

系统维护独立的用量聚合表（usedata 系列），按时间粒度预聚合，避免每次看板查询都扫描全量日志。

### 5.4 排行榜

`/api/rankings` 提供消费排行，可用于内部激励或成本关注。

## 6. 性能指标

`/api/perf-metrics` 提供系统级性能指标：

| 指标 | 用途 |
| --- | --- |
| 请求吞吐 | 容量规划 |
| 响应延迟分布 | 性能回归识别 |
| 错误率 | 故障早期信号 |

配合 `performance-metrics` 控制台模块查看。

### 6.1 性能设置

`/api/performance` 是 Root 权限的**性能统计与运维操作**端点（`/stats`、`/reset_stats`、`/disk_cache`、`/gc`、`/logs`），不是性能参数调节面。

可调的性能参数在 `/api/option` 中维护，对应 `setting/performance_setting/` 配置组。

## 7. 审计日志

管理写操作全部进审计（`audit_logs` 表），记录：

| 内容 | 说明 |
| --- | --- |
| 操作者 | 身份与角色 |
| 动作 | 如 `channel.delete`、`user.quota_add` |
| 目标 | 对象 ID 与关键字段 |
| 请求信息 | 方法、路由、状态码、成功与否 |
| 来源 IP | 客户端地址 |
| 前后值 | 如用户额度调整的前后余额 |
| 时间 | 操作时间 |

审计与认证事件**排除**密码、验证码、恢复码、私钥与可用的会话或认证令牌。

### 7.1 审计可见性

审计记录按角色隔离：管理员看得到完整操作明细，普通用户看不到他人的管理操作。

## 10. 多语言

控制台支持 **7 种语言**：

| 语言 | 标识 |
| --- | --- |
| 简体中文 | `zh` |
| 繁体中文 | `zh-TW` |
| 英语 | `en`（基准语言） |
| 法语 | `fr` |
| 日语 | `ja` |
| 俄语 | `ru` |
| 越南语 | `vi` |

后端有独立的 3 份语言文件（`en`、`zh-CN`、`zh-TW`），用于服务端消息与错误提示。

界面语言通过浏览器语言检测自动选择，可在控制台手动切换。

## 11. 边界与注意事项

| 事项 | 说明 |
| --- | --- |
| 日志库可独立 | 高吞吐场景建议把日志库与主库分离，避免影响业务查询 |
| `admin_info` 敏感 | 该字段内容对普通用户不可见，但管理员需注意其中的额度截断标记 |
| 审计只覆盖管理面 | 数据面的调用审计在消费日志中，两者分开 |
| 性能指标需正确配置 | 指标采集有开关，未启用时看板为空 |
| 上游请求 ID 依赖上游 | 部分上游不返回该字段，此时无法按上游对账 |
