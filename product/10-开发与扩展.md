## 2. 技术栈

| 层 | 选型 |

## 3. 代码结构

| 目录 | 职责 |
| --- | --- |
| `router/` | HTTP 路由、访问控制中间件、API 处理入口 |
| `middleware/` | 认证、限流、并发闸门、渠道路由等横切逻辑 |
| `controller/` | API 处理器与业务编排 |
| `relay/` | 上游适配器、协议转换、请求路由 |
| `relaykit/` | **独立可构建**的 Go 模块：协议 DTO 与转换 |
| `service/` | 业务逻辑（计费、渠道、认证、任务、并发等） |
| `model/` | 数据模型与持久化 |
| `setting/` | 分域配置（计费、倍率、模型、运营、系统、任务定价、性能等） |
| `constant/` | 全局常量（渠道类型枚举等） |
| `types/` | 跨层共享类型（如 `PriceData`） |
| `common/` | 通用工具与常量（配额换算、JSON 封装、日志、Redis 等） |
| `pkg/` | 内部库（计费表达式、JS 插件运行时、缓存、鉴权策略等） |
| `oauth/` | OAuth / OIDC 提供方实现 |
| `plugins/tasks/` | JavaScript 任务插件 |
| `web/` | Web 控制台 |
| `electron/` | 桌面封装与打包 |
| `docs/` | 架构决策、插件 API 规范、环境变量参考、认证指南 |

> 本表是**主要目录的概览**，不追求穷举；具体文件位置以 `rg` / codegraph 检索为准。

### 3.1 relaykit 的独立性

`relaykit/` 是**独立可构建**的 Go 模块，不依赖主模块：

```bash
cd relaykit && GOWORK=off go build ./...
```

主模块构建通过**不代表** relaykit 通过——改动 relaykit 或其公开 API 时必须单独跑上面这条命令。

## 4. 开发环境

### 4.1 启动

```bash
# 1. 构建前端（后端会内嵌 web/dist）
cd web
bun install --frozen-lockfile
bun run build
cd ..

# 2. 启动后端
go run .
```

### 4.2 前后端分离开发

```bash
# 终端 1：后端
go run .

# 终端 2：前端
cd web
bun run dev -- --port 5173
```

打开 http://localhost:5173 ，开发服务器把 API 代理到后端 3000 端口。

### 4.3 Makefile 目标

| 目标 | 用途 |
| --- | --- |
| `make dev` | 同时启动前后端开发 |
| `make dev-api` / `make dev-api-rebuild` | 启动后端（后者带重建） |
| `make dev-web` | 启动前端开发服务器 |
| `make build-web` / `make build-all-web` | 构建前端 |
| `make start-api` | 启动后端 |
| `make test` | 运行 Go 模块测试 |
| `make reset-setup` | 重置首次安装状态 |

容器化开发后端见 `docker-compose.dev.yml`。

## 5. 校验命令

### 5.1 Go

```bash
make test                                        # 根模块 + relaykit 两模块的测试（内部已用 GOWORK=off 隔离）
cd relaykit && GOWORK=off go build ./...          # relaykit 独立构建
```

> `make test` 内部对根模块与 relaykit **都加了 `GOWORK=off`**，因此它已覆盖 relaykit 的隔离测试；上面的独立构建命令是额外的快速自检。

### 5.2 前端

```bash
cd web
bun run typecheck     # tsgo -b
bun run lint          # oxlint
bun run test          # vitest run
bun run build         # rsbuild build
```

> 用 `bun run test`（vitest），不要用 `bun test`——后者是 Bun 内置的测试运行器，会静默跳过 vitest 配置。

### 5.3 i18n

```bash
cd web
bun run i18n:sync    # 同步翻译文件
```

### 5.4 插件

```bash
cd web
bun run lint:plugins         # oxlint 检查插件
bun run format:plugins       # oxfmt 格式化
```

## 6. 代码约定

这些是项目级硬约束，违反会被 review 打回。

### 6.1 数据库兼容

任何影响数据库行为的改动必须在 **SQLite、MySQL ≥5.7.8、PostgreSQL ≥9.6** 三种真实实例上验证。schema 与迁移类改动还需在全新库与旧版本升级库上各跑两遍启动，证明幂等。

单测、mock、构建成功、代码审查、只测一种方言——**都不算验证**。

### 6.2 计费安全

| 禁止 | 正确做法 |
| --- | --- |
| `int(float64(quota) * ratio)` | `common.QuotaFromFloat` |
| `int(math.Round(...))` | `common.QuotaRound` |
| `int(decimal.IntPart())` | `common.QuotaFromDecimal` |
| 直接写 `PriceData.OtherRatios` | `types.PriceData.AddOtherRatio` |

所有会成为计费乘数的用户可控量必须在**请求校验层**设上界，越界返回 400——具体边界与校验位置见 `.agents/rules/billing.md`（该文件是计费安全约束的权威来源）。

### 6.3 JSON 入口

主模块业务代码**不得**直接调用 `encoding/json` 的 marshal/unmarshal，统一走 `common.Marshal` / `common.Unmarshal` / `common.UnmarshalJsonStr` / `common.DecodeJson` / `common.GetJsonType`。

`relaykit/` 内使用 `kitutil.*`；直接调用编码器只允许出现在 codec 实现中。

### 6.4 行锁入口

`model/` 中用 GORM 查询方法构造的 `SELECT ... FOR UPDATE` 必须用 `lockForUpdate(tx)`。

**不要**用 `tx.Set("gorm:query_option", "FOR UPDATE")`——GORM v2 会静默忽略它，根本没加锁。

### 6.5 可选字段的零值语义

客户端 JSON 解析后要转发给上游的请求结构，**可选字段必须是指针类型并带 `omitempty`**（`*int`、`*uint`、`*float64`、`*bool`；切片 / map / 嵌套结构同样适用）：

- 客户端没传 → 变成 `nil` 并被省略
- 客户端显式传 `0` / `0.0` / `false` / 空数组 / 空对象 → 保持非 `nil` 并原样发给上游

非指针字段配 `omitempty` 会**静默丢掉显式的零值**。relaykit 的 DTO 转换层必须保持指针语义，解引用前先判空，否则会把这个约定打破。

### 6.6 前端组件复用

新增 UI 前先在 `web/src/components/` 与相关 `web/src/features/` 中找已有实现。**按用途和行为找，不是按你打算取的名字找。**

已有共享业务组件能覆盖的场景就该复用——引入 `Button` 或 `AlertDialog` 不算复用，如果 `CopyButton` 或 `ConfirmDialog` 已经提供了该行为。

### 6.7 Intl 语言代码

`zhCN` / `zhTW` **不是**合法的 Intl locale。任何进入 `Intl.*`、`toLocaleString` / `toLocaleDateString` / `toLocaleTimeString`、locale 感知格式化器的界面语言，必须先过 `@/i18n/languages` 的 `toIntlLocale`。

`project/intl-locale` 的 oxlint 错误**不得**用 disable 注释绕过。

### 6.8 受保护的项目信息

**绝不可**修改、删除、替换或隐藏对 **new-api**（项目身份）或 **QuantumNous**（组织/作者）的任何引用。这覆盖 README、许可证头、版权声明、包元数据、HTML 标题、meta 标签、页脚、关于页、Go 模块路径、包名、导入路径、Docker 镜像名、CI/CD 引用、部署配置、注释、文档与变更日志。

### 7.1 插件开发要点

改插件前必读 `docs/plugin-api/v1.md`（含描述撰写与翻译约定）。改契约时 `.md`、`.schema.json`、`.d.ts` 三者保持一致。

数值型 `usageSchema` / `usageProfiles[].schema` 字段的 `description` **必须命名计费主体 + 单价**（如 `Video generation unit price` / `视频生成单价`），单位放 `unit`，字段值仍是用量数量。

**元数据措辞需要显式复核**——编译通过、Schema 校验通过、测试通过都验证不了描述文案是否合规。
