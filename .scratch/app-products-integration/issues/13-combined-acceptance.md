# 13: 验收完整 App 产品链路并汇总可发布证据

**What to build:** 在可复现环境中演示 Supabase 登录、个人 App Key、指定用户充值、积分与报价、广场发现、用户/后台范围切换的完整产品流程，并给出实际验证证据及明确的未解决项。

**Blocked by:** 07 — 管理员控制 App 展示，并提供应用广场入口；09 — 钱包主区域显示当前 App 的订阅、套餐与商品；10 — 当前 App 充值、订单历史与到账状态形成闭环；11 — 后台用户、额度调整、套餐、商品和订单统一 App 范围；12 — Supabase 原生登录接通托管 Key、积分和收银台参考流程

**Status:** draft — 待确认拆分及 tracker 后，以 ready-for-agent 发布

- [ ] 汇总前序 ticket 的实际测试与数据库证据，任何缺失不以“最后集成已通过”代替；确认 checklist 的未勾选项及具体阻塞。
- [ ] 用两位用户、两个 App 和平台钱包完成真实 Supabase 登录、显示不同比例积分、quote、充值、支付确认、AI 消耗及余额刷新。
- [ ] 验证代理余额/Key/订单归属一致且订阅全路径拒绝，OAuth 用户订阅独立正常；同邮箱、同 App 两来源 user_id 不同且不共享资产，重复回调和异步完成不会双入账或双扣。
- [ ] 验证受控开户同元组并发唯一、跨 App 同人不同 ID，响应/映射写入丢失可恢复且不重新启用停用账户；规范化 App 钱包 1000/比例100 返回10积分，旧 OAuth 平台9000/App1000语义保持，代理仅访问绑定 App。
- [ ] 验证轮换上限100已用90仍余10，旧/新凭据及在途预留共用预算，结算/退款与恢复无重复；未支持预算连续性时明确拒绝受限轮换。
- [ ] 验证 Key 轮换各阶段失败可恢复、停用前订单付款仍可查账、比例快照/null、旧 credits 字段兼容和新客户端单位一致。
- [ ] 09/10/12 完成后核对每种身份与 OAuth 关闭状态的资产入口，确认余额、订阅（仅 OAuth）、充值及订单可达，再移除“各 App 订阅与积分”；不重建汇总卡或恢复已关闭 OAuth 的下拉选项。此项是具体 UI 清理交付，不仅是证据汇总。
- [ ] 用户与后台切换覆盖快速切换、换账号、失效选择、支付中换范围、停用/隐藏 App，不能串数据或执行到错误钱包。
- [ ] 从导航进入应用广场，展示开关与访问地址生效且无秘密泄露；旧品牌和归属完整。
- [ ] 对未配置积分的旧 App、平台 Key、OAuth 子 App、历史订单与订阅进行升级兼容演示。
- [ ] 双模式及仅单一模式验证通过；关闭 OAuth 后配置/顶部钱包选项隐藏，Supabase 托管链路继续工作，后台独立筛选仍能处理该 App，既有任务结算无丢失。
- [ ] 支付沙箱、Supabase 项目和回调需要的临时 tunnel 记录实际非秘密标识与命令，验收后清理临时来源和 redirect 配置；无沙箱/凭据时明确真实支付验收未完成。
- [ ] 确认受影响数据库的准确版本、空库/发布版升级/两次启动、相关日志库验证结果均有记录；独立模块受影响时附 GOWORK=off 构建证据。
