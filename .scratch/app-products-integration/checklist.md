# App 产品接入验收 Checklist

日期：2026-11-18。所有未勾选项均为待开发/待验收；本文不是测试结果。规格是行为定义的来源，本表用于核对覆盖与记录证据。

## A. 设计与发布

- [ ] A01 用户确认公开 HTTP API 与跨系统浏览器流程两个主要测试边界。
- [ ] A02 用户确认 13 张 ticket 的粒度、真实依赖及范围；需拆合的项已更新。
- [ ] A03 运行 /setup-matt-pocock-skills，确认 tracker 与 triage 标签；当前本地文件仍是草稿。
- [ ] A04 按依赖顺序发布规格与 tickets，记录真实标识和阻塞边；未修改或关闭父 issue。

## B. Supabase 与托管 Key（01、03、12）

- [ ] B01 用户只登录 Supabase 即可查余额、调用 AI 和发起充值，无 new-api OAuth 跳转。
- [ ] B02 身份验证拒绝伪造、过期和其他项目的凭据；目标用户从可信映射解析。
- [ ] B03 01 的受控代理开户事务原子写入账户/来源/App/唯一外部身份，返回稳定 ID；同元组并发唯一、响应丢失/映射写失败可恢复，冲突与越权拒绝、不复活停用账户；不复制 OAuth 映射，不以普通 CreateUser 冒充。
- [ ] B04 PAT、个人 Key、高权限 Supabase 密钥均不出现在浏览器、可读 metadata、公开响应或日志。
- [ ] B05 管理员按明确 role/scope 创建、更新、停用、轮换指定用户的 App Key；原 self 接口不可越权。
- [ ] B06 代理 App Key 只扣指定 App 的余额，不选择或回退 App/平台订阅；余额不足即拒绝，其他用户、App 与平台资金不受影响，Key 限额独立生效。
- [ ] B07 模型/IP/组限制、App 白名单、App 停用、Key 撤销及缓存失效生效。
- [ ] B08 同步、流式与异步任务的预扣、差额、失败退款及任务读取隔离均归属同一 App。
- [ ] B09 平台旧 Key 和 OAuth 旧路径回归通过。
- [ ] B10 正常轮换按创建、保存、验证、切换、撤销执行；响应丢失/保存失败/并发可恢复，旧 Key 不提前撤销，紧急撤销独立立即生效；轮换共享原预算及在途预留/结算/退款，上限100已用90仍余10，旧新并发不能超额，不能复制计数或重复退款；缺预算连续性时拒绝受限轮换。
- [ ] B11 Key 周期/窗口规则仅限制消费，不表示订阅或充值；绑定验证目标用户所有权，不能误用 PAT 持有人的规则或静默跳过限制。不把独立未提交开发当成已发布合同，不重复开发规则引擎。

## C. 指定用户收银台（02、09、10）

- [ ] C01 管理员 PAT 为指定用户、显式平台或 App 创建订单，返回可用收银台链接。
- [ ] C02 普通 PAT、scope 不足、失效 PAT、无效目标和非法范围被拒绝；停用拒绝新下单，但允许授权读取/对账已有订单。
- [ ] C03 服务端确定用户价格组、金额、货币和到账 quota；负数、越界和客户端篡改失败。
- [ ] C04 同幂等键同参数返回原订单；不同参数冲突；网络超时能查订单恢复。
- [ ] C05 订单快照原子固定用户、来源、App、购买目标、货币、金额、到账 quota 与比例；未配置比例显式 null，旧无快照订单不套当前比例，切换不改归属。
- [ ] C06 webhook 错签名、金额/货币不符与非法状态不入账；重复成功通知仅入账一次。
- [ ] C07 浏览器回跳和余额变化不作为支付成功证明；订单查询只能看到授权目标。
- [ ] C08 付款方式按已支持矩阵展示；未配置/不支持时明确失败，不退回平台钱包。
- [ ] C09 代理可查询本人充值/一次性商品订单，不能购买或授予订阅；OAuth 订阅结果仍按其本人来源与范围查询。
- [ ] C10 停用前有效订单继续按原快照处理真实付款并可查账；过期后真实付款有可审计异常处理，不静默丢款或恢复调用权限。

## D. 积分与 quote（04、05、06）

- [ ] D01 管理员能配置每 App 的 quota_per_credit，旧 App 未配置时保持原显示。
- [ ] D02 0、负数、小数及超上限比例被拒绝，修改比例显示已有余额单位变化提示。
- [ ] D03 同样 100000 quota，比例 1000 得 100 积分，比例 100 得 1000 积分。
- [ ] D04 独立规范化钱包返回所选 app_id 的 quota/用量/积分/比例，平台比例和积分为 null；会话、管理员 PAT、待开发 token 固定 App 的 OAuth 入口返回同一 DTO。App1000/已用200/比例100返回10积分及已用2，旧 OAuth 平台quota9000/App1000字段不变；积分为十进制字符串，最多6位向下截断。
- [ ] D05 正消耗低于显示精度时界面提示小于最小单位；无限额不显示成零额度。
- [ ] D06 quota=1000、used_quota=200 时显示余额 1000 quota 对应积分，不错误显示 800。
- [ ] D07 定价/PAT 读取与原 OAuth 读取兼容；quote 返回 estimated_credits，不把估算标为实际结算。
- [ ] D08 提交前价格/比例变化触发更新报价确认；已有订单按原快照解释，账本不受比例修改影响。
- [ ] D09 修改比例不改变 quota、模型价格、支付金额、实际扣费或退款。
- [ ] D10 旧 quote.credits 保持原始 quota 的数值语义并弃用，新 estimated_credits 为 string|null；StudioClient 与类型迁移，新旧客户端分别验证。
- [ ] D11 报价确认绑定服务端版本/摘要、用户、来源、App 及输入；变化重新确认，代理估算不混入订阅权益。

## E. 应用广场（07）

- [ ] E01 默认关闭展示；管理员可编辑开关、简介、独立访问地址及排序，复用现有名称/图标。
- [ ] E02 只有展示开启且启用的 App 出现在可从导航进入的广场，排序稳定，链接可访问。
- [ ] E03 公共 DTO 只含展示字段；非法 URL、脚本链接及不安全外链处理被拒绝。
- [ ] E04 关闭展示不影响已有钱包、订阅、Key；停用行为与隐藏行为可区分。
- [ ] E05 new-api、QuantumNous 品牌与归属完整保留。

## F. 用户钱包与后台（08、09、10、11）

- [ ] F01 普通用户与管理员均可选择平台/App；列表、持久化与失效选择按账户授权处理。
- [ ] F02 标题、余额、用量和请求数属于同一所选范围；请求数明确窗口，未知显示暂无数据。
- [ ] F03 OAuth 本人主区域显示当前 App 订阅、套餐、商品；代理无订阅 UI/权益，能力按用户来源而非 App 开关判定。
- [ ] F04 09/10/12 完成并在 13 验证各来源资产入口后移除“各 App 订阅与积分”；09 不提前删除，OAuth 关闭历史仍有独立只读入口。
- [ ] F05 充值档位、确认弹窗与订单历史按同一范围；切换清空未提交操作，保留已创建订单原归属。
- [ ] F06 邀请/兑换/转入等平台专属操作不在 App 视图暗中执行到平台。
- [ ] F07 快速切换、响应乱序、退出换账户、旧选择恢复不会串数据或串单位。
- [ ] F08 零余额、无订阅、加载、错误可重试、停用 App 历史查看均有明确状态。
- [ ] F09 后台列表、排序、搜索、额度调整、套餐/商品详情与订单补单均校验范围和权限。
- [ ] F10 七语言、数字格式 locale、键盘操作、移动端和深浅主题回归通过。

## G. 交付证据（各 ticket 自验，13 汇总）

- [ ] G01 每张 ticket 附实际测试命令、观察结果与未解决项，验收项不是仅凭构建通过勾选。
- [ ] G02 数据库相关 ticket 记录真实 SQLite/MySQL/PostgreSQL 版本、测试命令和结果。
- [ ] G03 schema 相关 ticket 验证空库、最新发布版升级与两次启动幂等；相关独立日志库同步覆盖。
- [ ] G04 受影响独立 Go 模块用 GOWORK=off 单独构建；不受影响时明确记为不适用。
- [ ] G05 认证相关 ticket 附 OWASP/ASVS 版本、适用要求与回归证据，不虚构合规结论。
- [ ] G06 各功能前端类型检查、lint、行为测试与适用生产构建通过。
- [ ] G07 沙箱支付、真实 Supabase 登录和真实目标钱包的组合验收通过；秘密不进入报告。
- [ ] G08 公网 tunnel 主机名、测试项目与实际命令有记录，临时配置验收后清理。
- [ ] G09 框架 skill、starter、参考实现与公开 SDK/API 契约同步；CLI 变更时两个打包 skill 同步。
- [ ] G10 实现分支 merge-base 审计记录基线、文件范围、分级发现、修复及遗留，无未解释 High 问题。
- [ ] G11 skill 入口与相关参考默认优先代理模式，OAuth 按需启用；代理路径不自动运行 OAuth bootstrap，现有 OAuth 示例及待开发接口均明确标注能力边界。

## H. 双接入模式与开关（01、03、08、11、12）

- [ ] H01 创建 App 可选仅托管 Key、仅授权登录或双模式；新建默认与旧 App 迁移默认明确且验证兼容。
- [ ] H02 OAuth 开启显示授权配置，关闭隐藏并取消对应必填；原配置安全保留，公共响应不泄露隐藏秘密。
- [ ] H03 托管 Key 模式不要求 OAuth 回调、client_secret 或二次登录，通用积分/支付/广场配置不被授权开关隐藏。
- [ ] H04 Key 创建时固定 user_id + app_id，后台显示并按 App/用户/状态筛选，禁止事后直接改 Key 归属。
- [ ] H05 关闭 OAuth 的 App 从顶部/钱包下拉隐藏；当前选择回平台，未提交操作清理，不串余额或单位。
- [ ] H06 关闭 OAuth 不停用另一模式的 Key、不删除 Supabase 会话/映射、不删除资产；后台独立筛选仍可管理该 App。
- [ ] H07 关闭某模式时对应授权/调用新入口服务端拒绝，不能靠隐藏 UI 代替校验；已受理异步任务仍可完成结算/退款。
- [ ] H08 模式、整体启用与广场开关分别生效，隐藏 App 不等于停用，后台能够筛选三种接入组合。
- [ ] H09 双模式用户独立、不关联、不共享 user_id/资产；同邮箱和 Supabase 自动关联歧义不能绕过来源校验，同一自然人跨 App 的代理 user_id 也不同，代理账户 App 归属不可变且不能创建其他 App Key，原有 OAuth/平台账户跨 App 行为不变。
- [ ] H10 代理 subscription_supported=false，读取/购买/授予/抵扣均拒绝；含双模式 App 及异常残留订阅；OAuth 订阅回归正常。
- [ ] H11 后台独立按用户来源和 App 接入组合筛选；代理参考接入不依赖 09，后台 skill 不要求原生 Supabase 管理员先登录 OAuth。
