# App 服务端接入、积分、应用广场与钱包切换规格

日期：2026-11-18。状态：完整草稿，待确认测试边界与 ticket 拆分；尚未发布 tracker，尚未开发。

## Problem Statement

子 App 已有 Supabase 用户体系，并希望由 App 后端托管每个用户的 AI Key。现有可运行参考实现以 new-api OAuth/OIDC 登录为路径，用户需要额外跳转；管理员 PAT 也不能直接通过现有 self 接口为指定用户创建订单或管理其 Key。框架 skill 已先调整为默认优先推荐代理模式，所需接口与参考实现仍待开发。

不同 App 希望采用不同积分单位，客户端需要读取服务端提供的余额和报价积分。当前没有 App 级换算配置，也没有应用广场展示开关。

控制台虽然已有管理员 App 选择器，但钱包主区域仍展示平台数据，下面单列“各 App 订阅与积分”；普通用户看不到选择器。用户很容易把平台余额、App 余额、订阅额度和充值目标混淆。

## Solution

保留 Supabase 登录，由可信 App 后端验证用户身份、维护稳定的 new-api 用户映射、托管该用户的 AI Key，并通过管理员 PAT 调用明确支持指定用户的管理与收银台接口。

双模式仅表示同一 App 提供两条独立接入路径，不关联两边用户。代理用户与 OAuth 用户使用不同的 new-api 用户身份，不合并余额、订单、Key 或订阅。代理模式只使用对应 App 钱包余额，不支持订阅；周期性 Key 额度规则只限制消费，不代表订阅或新增资金。

每个 App 可配置 quota 与积分的比例，余额、用量、套餐和报价由服务端按统一规则返回积分；new-api 继续以 quota 为唯一账本。App 可由管理员选择展示到应用广场。

顶部 App 选择器同时提供给管理员和普通用户。切换后，钱包主区域显示该用户在所选范围内的余额、消耗、订单、充值及订阅；后台管理页面采用同样的范围语义，最终移除底部跨 App 汇总卡片。

## User Stories

1. 作为子 App 用户，我希望继续使用原有 Supabase 登录，以便无需再次登录 new-api。
2. 作为子 App 用户，我希望登录后使用自己的 AI Key 调用模型，以便消耗归属于我本人。
3. 作为子 App 运营者，我希望在后端托管用户 Key，以便浏览器无需持有网关秘密。
4. 作为子 App 运营者，我希望管理员 PAT 可以为指定用户创建收银台订单，以便用户在 App 内发起充值。
5. 作为用户，我希望支付后额度进入下单时确定的钱包，以便充值目标不会随页面切换改变。
6. 作为用户，我希望重复支付通知不会重复入账，以便余额可信。
7. 作为运营者，我希望查询指定用户、指定 App 的订单状态，以便可靠显示支付结果。
8. 作为运营者，我希望创建、更新、停用和轮换指定用户的 App Key，以便完成凭据生命周期管理。
9. 作为用户，我希望 App Key 调用只使用对应 App 的资金来源，以便其他钱包不会被误扣。
10. 作为管理员，我希望原有平台 Key 继续保持原行为，以便现有集成不受影响。
11. 作为用户，我希望 App 停用或 Key 撤销后调用被拒绝，以便权限能及时收回。
12. 作为运营者，我希望每个 App 可以定义不同积分比例，以便采用适合产品的积分单位。
13. 作为运营者，我希望修改比例前看到影响提示，以便知道已有余额的显示也会变化。
14. 作为客户端开发者，我希望余额接口直接返回积分及比例，以便无需重复编写换算逻辑。
15. 作为客户端开发者，我希望 quote 报价接口返回预估积分，以便在提交前展示消耗。
16. 作为用户，我希望预估与实际消耗明确区分，以便知道最后以结算为准。
17. 作为用户，我希望充值页同时显示真实支付货币和到账积分，以便了解购买内容。
18. 作为用户，我希望积分显示统一精度且小额不会误显示为免费，以便理解真实成本。
19. 作为管理员，我希望通过开关控制 App 是否在应用广场展示，以便逐步开放子产品。
20. 作为管理员，我希望配置图标、简介、访问地址及排序，以便用户识别和打开 App。
21. 作为广场访客，我希望看到可访问的子产品，以便发现合适的应用。
22. 作为用户，我希望隐藏的 App 仍可正常使用已有钱包，以便展示策略不影响资产。
23. 作为用户，我希望在顶部选择平台或自己的 App，以便查看对应余额。
24. 作为用户，我希望钱包标题与当前 App 一致，以便随时确认查看范围。
25. 作为用户，我希望切换后主区域直接展示该 App 的数据，以便无需向下寻找汇总卡。
26. 作为 OAuth 用户，我希望钱包积分与有到期时间的订阅额度分开显示，以便知道可用资金的性质；代理用户不提供订阅。
27. 作为 OAuth 用户，我希望套餐、商品、订阅记录与所选 App 一致，以便不会买错产品；代理仅提供充值/一次性额度商品。
28. 作为用户，我希望订单历史只展示当前范围的本人订单，以便看懂资金来源。
29. 作为用户，我希望快速切换时不会看到上个 App 的金额，以便避免误操作。
30. 作为用户，我希望没有钱包、没有订阅和请求失败分别展示明确状态，以便分辨零余额与加载失败。
31. 作为管理员，我希望用户列表、额度调整、套餐、商品和订单跟随当前 App，以便管理准确。
32. 作为管理员，我希望范围筛选不能绕过服务端授权，以便用户和 App 数据保持隔离。
33. 作为已有用户，我希望迁移后保留账户映射、余额、订单和订阅，以便资产与历史不丢失。
34. 作为集成开发者，我希望 skill、接口说明和示例同步支持服务端 PAT 模式，以便不再照旧文档接回 OAuth。
35. 作为维护者，我希望现有 OAuth 模式继续可用，以便已有子 App 能逐步迁移。
36. 作为管理员，我希望创建 App 时选择托管 Key、授权登录或双模式，以便同一套 App 管理兼容不同身份系统。
37. 作为管理员，我希望关闭授权登录后隐藏授权配置与该 App 的顶部/钱包下拉选项，以便界面只展示实际启用的授权入口。
38. 作为子 App 运营者，我希望关闭 OAuth 后 Supabase 与托管 Key 仍正常工作，以便独立使用原有登录体系。
39. 作为管理员，我希望创建 Key 时明确绑定用户与 App，以便资金、模型限制和用量都能按产品归属。
40. 作为管理员，我希望后台按接入模式、App、用户与 Key 状态筛选，以便仍能管理不出现在顶部切换器里的产品。
41. 作为运营者，我希望双模式的用户完全独立，以便登录方式变化不会关联账户或共享资产。
42. 作为代理用户，我希望界面和接口明确不支持订阅，以便不会购买无法使用的权益。
43. 作为运营者，我希望 Key 轮换失败可以恢复，以便网络中断不会使用户丢失可用凭据。

## Implementation Decisions

以下是待审阅的实现约定；接口名称和字段是拟议契约，不表示当前已经支持。实现时优先兼容扩展已有接口。

### 0. 双接入模式、开关与 App 关联

- 同一 App 可启用“后端托管 API Key”和“new-api OAuth/OIDC 授权登录”中的一种或两种。采用 api_key_enabled、oauth_enabled 两个独立布尔配置；App 整体启用状态、广场展示开关与它们分别控制，不混为一个开关。
- 两种模式的用户独立、不关联、不共享 new-api user_id；即使邮箱相同也不合并，不提供跨模式关联、余额转移或订阅共享。服务端持久化可信身份来源（proxy / oauth）与用户归属，不能由请求中的 mode 临时决定。此身份来源属于用户，不能从 App 的双模式开关推断。
- 创建界面以接入方式选择展示三种有效组合：托管 Key、授权登录、双模式。新 App 默认托管 Key 开启、OAuth 关闭；已存在 App 迁移为 OAuth 开启、托管 App Key 关闭，保持既有 OAuth 和平台 Key 行为。启用的 App 至少有一种接入方式；停用 App 可以暂存两者关闭的配置。
- App 即使不启用 OAuth，也必须有稳定 app_id；已有 client_id 保持稳定，不把 OAuth client_id 当作 Supabase 用户 ID。托管 Key 模式创建不要求填写 redirect URI、OAuth scopes、公私客户端模式或生成 client_secret；Supabase 项目关联只在托管接入说明需要时展示，不作为任意 JWT 的信任凭据。
- oauth_enabled 开启时显示回调地址、登出回调、scope、公私客户端及必要 secret 管理；关闭时这些授权专属配置隐藏且不参与必填校验，已保存的配置在服务端保留以便再次开启，不返回隐藏的秘密。
- api_key_enabled 开启时显示后端接入说明、App 标识、托管 Key 与 PAT scope 提示；关闭时隐藏这些专属操作。积分、支付、基础产品资料与广场配置为通用配置，不随 OAuth 开关隐藏。
- Key 在创建时由可信后端配置确定目标 app_id，并固定关联“new-api user_id + app_id”；同一自然人在不同 App 必须分别开户，使用不同的代理 new-api user_id 与 Key；代理账户的 App 归属不可变，不能绑定其他 App。此约束不改变原有 OAuth 用户与平台账户的跨 App 行为。App Key 不能事后改归属，需创建新 Key 并撤销旧 Key；平台 Key 默认 app_id=0，不自动迁移或猜测归属。
- 服务端在 OAuth 授权、换码、刷新及 App access token 的新请求入口检查 oauth_enabled；关闭后这些新请求拒绝，但不清除 Supabase 会话、不停用另一种模式的 Key，也不打断已受理任务的最终结算/退款。托管接入开关同理控制其新调用，不阻断必要的后台结算和资产管理。
- 已由用户明确选择：oauth_enabled=false 的 App 也从顶部/钱包 App 切换下拉框隐藏；不是只隐藏授权表单。下拉选项筛选与服务端授权分开，隐藏不删除关系、余额、Key、订阅或历史订单。
- 关闭当前选中 App 的 OAuth 时，顶部/钱包选择验证后切回平台，清理未提交操作；不得在平台标题下继续展示旧 App 余额。开启后，在满足本人关联或管理员查看权限时重新进入选项。
- 对只开托管 Key 的 App，代理用户在子 App 查询自身积分和充值订单，不提供订阅；new-api 顶部钱包不提供切入该 App 的选项。后台 App 管理、Key 管理和财务管理必须保留独立的全量授权范围筛选：按 App 接入组合、用户身份来源、App、用户、Key 状态组合筛选，不能复用已过滤的顶部选项作为唯一数据来源。
- 后台列表标注“托管 Key / 授权登录 / 双模式”、整体状态与广场展示状态；Key 列表明确所属 App。管理员即使关闭某 App 的 OAuth，仍可在这些管理页找到并处理其已有资产。

### 1. 身份与授权边界

- Supabase 继续作为子 App 身份源。浏览器请求只携带 Supabase 会话；App 后端验证签名、有效期和项目身份后，从可信会话确定用户。
- 代理映射唯一键为受信任的 Supabase 项目、原生用户 UUID、App 及 proxy 来源，绑定独立的代理 new-api 用户。只复用已有可信的同来源映射；现有 OIDC profile/new-api user_id 原样保留供 OAuth 使用，不复制到代理映射，不按邮箱或同一 Supabase UUID 自动关联。
- 同时提供两种登录时，在创建映射前验证已选入口与已验证身份的来源；若 Supabase 自动关联产生同一身份承载两种来源，不能复用同一网关用户，需隔离身份域或拒绝有歧义的会话。代理专用网关账户不提供用户可用的网关密码/原生登录入口，也不向其发放 OAuth 用户令牌；服务端拒绝跨模式绑定和直接指定另一来源 user_id。
- 01 交付受控代理开户/恢复合同（待开发，具体路由实施时确定）：管理员 PAT 具备匹配的用户创建/读取权限，服务端校验固定 App、受信项目/issuer 和由 App 后端验证的原生 subject；外部身份键采用无歧义规范编码，不使用邮箱。平台级 PAT 仍可管理其他 App，App 隔离依赖后端固定配置与网关归属校验，不能误称 PAT 已按 App 授权。
- 网关在同一事务内创建账户、写入受保护 proxy 来源与不可变 App 归属、建立唯一外部身份绑定；成功返回稳定 user_id、source、app_id，不返回生成密码或 Key。保留普通管理员开户旧合同；现有 CreateUser 未提供上述绑定和返回 ID，不能直接作为代理幂等开户实现。
- 同一（项目/issuer、原生 subject、App、proxy）首次并发/重试只返回一个账户；另一 App 返回另一 user_id。按稳定外部身份恢复不依赖客户端保存首次响应或仅依赖短期幂等键，参数/归属冲突拒绝，不覆盖绑定、不重新启用已停用账户。查询/恢复同样校验管理员权限与归属，不允许普通用户认领。网关成功后才保存 Supabase 映射，响应丢失或映射写入失败时重试取回同一 ID；Key 初始化单独幂等恢复，账户不提供可用的原生/OAuth 登录凭据。
- PAT 与用户 Key 只存服务端秘密存储或受保护的凭据表，禁止进入客户端 bundle、普通 profile、用户可编辑 metadata、日志和公开 API。Supabase 高权限密钥也只在后端使用。
- new-api 管理员 PAT 的权限仍是平台级管理员授权，不因请求携带 app_id 就变成 App 专用凭据。App 后端必须验证自己的映射与配置；网关验证角色、scope、目标用户和 App 状态。不得声称现有 PAT 已有 App 级授权限制。
- 指定用户的支付使用管理员权限及 billing:write，读取使用 billing:read；指定用户的 Key 管理使用管理员权限及对应 api_key scope。保持现有普通用户 self 接口只能操作本人，不通过全局覆盖请求身份实现代理。
- 每次代理操作记录操作者、目标用户、App、订单或 Key 标识、结果与请求关联标识，排除秘密。

### 2. 指定用户收银台

- 新增明确的管理员代理下单与订单查询能力。下单必须包含目标 user_id、显式 app_id、购买类型和服务端可验证的金额或商品/套餐 ID；app_id=0 表示平台，正数表示对应 App，缺失目标范围拒绝。
- 首个完整切片采用现有 Waffo Pancake 充值链路，保留平台既有路径并支持代理 App 钱包；代理身份只能操作其绑定 App，不能向平台或其他 App 下单。代理模式只支持充值及一次性额度商品；不新增 PAT 代理订阅 checkout。OAuth 用户订阅仍沿用原授权/控制台入口及支付矩阵。未支持的方式明确返回不可用，不能静默退回平台支付。
- new-api 以目标用户的实际分组与价格规则计算金额和到账 quota；客户端提交的积分、折扣、价格和身份不能决定账本结果。
- 复用现有 checkout 业务核心、支付校验及 webhook 入账事务，不复制一套钱包或支付结算。浏览器返回页和余额变化都不是某个订单支付成功的证明，必须查询绑定目标的订单终态。
- 订单创建时固定 user_id、app_id、购买目标、货币、支付金额、到账 quota；不得由随后切换的 UI 状态或回调参数改写。订单摘要固定当时的换算比例，以便后续比例调整时仍能解释购买内容。
- 订单同时固定身份来源；快照包含 quota_per_credit（未配置时显式 null），旧订单缺快照按原货币/quota 展示，不套用当前比例。新建订单原子读取并写入比例快照；实现依赖 04 的配置合同。
- App/模式停用禁止新下单，不禁止授权查看既有订单和对账；已创建有效订单的真实支付回调仍按原快照恰好一次入账，不因当前开关丢失支付结果，也不恢复新 AI 调用。保持独立的历史读取/管理员路径供已关闭 OAuth 的资产查账，不将其重新加入钱包下拉。过期未支付订单不可复用；订单过期后收到真实付款必须进入可审计异常处理，不伪造失败或静默丢款。
- 对重复下单使用幂等键，相同操作者、目标和参数返回原订单；同键不同参数返回冲突。网关超时后可查询并恢复，不盲目重建订单。
- 无效签名、错商户、金额或货币不符、无效状态转换不能入账；重复通知至多入账一次。支付配置缺失及现有合规确认门槛继续生效。

### 3. 后端托管 App AI Key

- 当前普通 Key 没有 App 归属，而 OAuth 调用已有 App 资金上下文。为 Key 增加不可随请求改写的 App 归属，默认 0 保持平台行为；正数 Key 绑定用户与 App，管理端显示归属。
- 管理员可为指定用户创建、查看脱敏信息、修改限制、停用、轮换 App Key。创建或轮换仅在授权的服务端响应中返回新秘密；普通列表和广场不得返回 Key。
- 复用现有 token 限额、模型、IP、组限制和缓存失效机制；App 白名单及停用状态必须同样作用于 App Key。截图中的“额度规则/配额管理”是 Key 的周期或窗口消费限制，不是钱包、充值或订阅；工作区出现了独立未提交的 TokenQuotaRule/绑定开发，本轮不修改或宣称其已交付，也不重复开发规则引擎。若目标实例支持规则，指定用户 Key 只能绑定其本人拥有且允许该范围的规则，不能误用管理员 PAT 持有人的 self 规则；已绑定限制不可因能力判断而静默跳过，未支持时明确不可用。
- App Key 建立 App 资金上下文，复用现有预扣、结算、退款与 App 任务隔离，但资金来源固定为余额：不得选择、消耗或回退到 App/平台订阅。余额不足即拒绝，即使有异常残留订阅也不能抵扣。Key 限额只是消费上限，不是独立可充值的钱包，不得通过充值 Key 限额代替钱包入账。
- Key 轮换按“创建替代 Key → App 后端安全保存并验证 → 切换使用 → 撤销旧 Key”进行，不宣称网关与凭据库存在跨系统原子事务。以轮换操作 ID 去重和追踪；返回秘密丢失时通过受控恢复或撤销不可恢复的替代 Key 后重试，旧 Key 在正常切换确认前继续有效。显式紧急撤销不等待此流程，已受理任务仍独立结算。覆盖每一步中断、重试和并发，不向普通读取接口开放秘密。
- 轮换必须让旧/新凭据共享同一逻辑消费预算，保留累计上限、剩余额度、周期已用量及在途预留；换 Key ID 不得重置计数。旧 Key 已受理任务的结算/退款仍归原预算，不能靠一次性复制计数处理并发；未具备预算连续性时明确拒绝受限 Key 轮换，不能静默放宽限制。验收：上限 100、已用 90，轮换后仍只可用 10，旧/新并发合计不超过原上限，重复恢复不重复预留或退款。
- 同步、流式及已支持异步任务均须使用同一 App 归属。持久化任务的归属保证后台完成结算时不依赖浏览器会话。
- 不把管理员 PAT 传给 AI relay，不要求每个用户创建 PAT，不新增 OAuth 登录步骤。也不把 JWT 免刷新当作服务端 Key 模式的撤销保证。

### 4. App 积分定义

- App 配置 quota_per_credit，定义“多少 quota 等于 1 积分”。第一版只支持正整数，上限不超过现有安全整数额度边界；空值表示未启用 App 积分显示。拒绝 0、负数、小数和越界数值。
- 未配置的旧 App 保持原额度/货币展示，不擅自给旧余额指定新单位；配置后所有当前余额与累计用量按该比例显示。修改比例只改变展示单位，不改变原始 quota、模型价格、订单金额和订阅实际额度。
- 积分值以十进制字符串返回。正数 quota 除以比例后最多保留 6 位小数并向下截断；精度规则固定，不新增每 App 精度配置。正 quota 换算结果不足最小显示单位时，界面显示“小于 0.000001 积分”，不能标为免费。
- 使用十进制安全运算，积分展示结果不反向参与扣费。无限额沿用明确的无限额状态，不把 0 或特殊哨兵换成 0 积分余额。
- 示例：100000 quota、quota_per_credit=1000 返回 100 积分；同样 quota、比例=100 返回 1000 积分；1 quota、比例=3 显示 0.333333 积分。修改比例必须提示已有余额显示会变化。

### 5. 余额、定价与 quote 契约

- 明确 quota 是账本额度，quote 是提交前报价；两者都覆盖，不凭名称混为同一接口。
- 提供当前用户的范围化钱包读取，以及管理员 PAT 的指定用户读取。返回实际 user_id、app_id、quota、used_quota、quota_per_credit、credits、used_credits；无比例时积分字段为 null。采用独立的规范化钱包读取合同，不改写旧 /oauth/userinfo：新响应 quota/used_quota 只表示响应 app_id 对应范围，积分只由该范围余额与当前 App 比例计算；平台 app_id=0 的比例/积分为 null，保持原货币显示。旧 OAuth quota/used_quota 继续是平台数据，app_quota/app_used_quota 继续是 token 所属 App 数据，不向旧接口混加含义不明的积分字段。
- 控制台会话读取本人授权范围，管理员 PAT 按权限读取指定用户；OAuth 通过待开发的 OAuth 钱包入口（api:read）读取 token 固定 App，不发送 dashboard PAT、不允许自选跨 App。具体新路由尚未实现，各入口返回同一 DTO；代理只读绑定 App，不提供平台钱包读取。
- 回归夹具：平台 quota=9000、App quota=1000、App used_quota=200、比例=100，新 App 钱包 credits="10"、used_credits="2"，不能显示 90 或 8；旧 OAuth quota=9000、app_quota=1000 保持不变，两模式及新旧客户端分别验证。
- quota 本身就是剩余额度，不能再次减去 used_quota。used_quota 为累计消耗，不把“剩余+已用”当成充值总额或订阅总额。
- 请求统计严格按 user_id 与 app_id 统计，并明确统计窗口；第一版允许按现有可追溯日志范围返回统计及其窗口，日志被清理时不能冒充终身总次数。无法可靠统计返回 null 并显示暂无数据，禁止用平台 request_count 填充 App 卡片。
- 定价读取必须支持可信 App 后端的 PAT 路径；返回该目标用户可见的定价与 App 比例，同时保持原 OAuth pricing 可用。
- 现有子 App 的 quote 由 App 后端输出 estimated_quota、estimated_credits 与使用的比例，继续复用现有业务估算；不在本次新增通用模型报价引擎。提交时重验价格/比例，发生变化则返回更新报价供确认。
- 现有参考 quote 顶层 credits 实际是原始 quota 数值：过渡期保持原字段及类型且标记弃用，新增 estimated_quota 与十进制字符串 estimated_credits（无比例时 null）。迁移 StudioClient 与相关类型到新字段，禁止同名旧字段悄悄改单位；旧客户端回归保持原语义。报价确认绑定服务端生成的报价版本/摘要和用户、App、来源及输入；提交重验，不信任客户端自报价格。
- 钱包响应提供来源对应的 capabilities：代理 subscription_supported=false；OAuth 按实际能力返回。代理订阅读取、购买、后台授予及扣费入口均明确拒绝 unsupported，不以空订阅列表假装可用；双模式 App 上也不能仅按 oauth_enabled 判定代理用户支持订阅。
- 实际消耗展示只读取网关结算数据，不能把 quote.total_quota 或估算退款字段标成已扣费/已退款。订单采用下单比例解释历史，普通余额与历史用量展示采用当前比例并明确单位口径。

### 6. 应用广场

- App 增加广场展示开关，默认关闭；配置简介、独立的 HTTPS 访问地址与排序，名称和图标复用已有字段。访问地址与 OAuth redirect URI 分开。
- 广场只展示开关开启且 App 启用的条目，稳定按排序与 ID 排序。关闭展示不影响已有 Key、余额、订阅与历史访问权限。
- 广场列表使用仅含公开展示字段的 DTO，不能返回 client_secret、PAT、Key、用户信息、Supabase 管理配置或钱包数据。
- 广场从站点导航可达，卡片复用项目已有组件，展示名称、图标、简介和“打开应用”。打开外链采用安全 URL 校验与新窗口保护。
- 第一版不做分类、搜索、评分、推荐算法、开发者自助审核或自动 SSO。保留全部 new-api 与 QuantumNous 现有品牌与归属信息。

### 7. 顶部切换与钱包 UI

- 复用现有 Active App 选择器、状态与钱包组件；补齐普通用户安全可读的 App 列表。选项为“平台”及 oauth_enabled=true 且与当前 new-api/OAuth 本人身份有关联的 App（钱包、订阅或已授权关系），不得把独立代理用户的资产加入当前账户；管理员顶部/钱包选项也应用 OAuth 开关筛选。广场公开可见性与此独立，管理页的全量筛选也与此独立。
- 广场列出可发现的产品，不自动授予任何财务查询权限。用户只能查看自己的数据；管理员保留现有可管理 App 范围。
- 选择器持久化必须按登录账户隔离，退出清理；无权或已删除的旧选择验证后回到平台。停用 App 的已有资产和历史仍可查看，明确标注停用并禁用新购买及调用。
- 页面标题显示所选钱包名称；主卡片、充值、套餐、本人订阅、商品和订单历史均使用相同范围。平台保持货币显示；已配置比例的 App 显示积分，付款显示真实货币。
- 钱包积分与订阅剩余额度分开，不合并无限额、到期额度和永久余额。订阅显示总额、已用、剩余、有效期及状态，套餐仅列出当前 App 可购买内容。
- 只有 09 的 OAuth 订阅/商品、10 的充值/订单及 12 的代理资产入口全部完成并在 13 验证后，才移除“各 App 订阅与积分”汇总卡；09 不单独删除。OAuth 关闭的历史用户仍有独立只读资产/订单入口，不重建底部汇总、不恢复下拉选项；代理用户通过子 App 查余额与订单。确保各来源旧用户仍能查到自己的资产。
- 查询键包含用户与 App，切换取消或忽略过期响应；标题、数字、单位、报价不能混用不同范围。切换清除未提交金额、商品选择及确认弹窗；已创建订单继续归属原范围。
- 无钱包是 0，无订阅是空状态，网络失败是错误状态并允许重试，缺少指标显示暂无数据。小屏、键盘、深浅色和七种语言覆盖现有使用方式。
- 平台专属的邀请奖励、转入余额及兑换码若不支持 App，App 视图隐藏并提示可切回平台；不把这些操作悄悄执行到另一个钱包。

### 8. 后台与交付范围

- 后台用户列表、搜索、排序和额度调整按当前范围使用同一 quota/积分语义；调整时展示原始 quota 与积分换算，仍以安全 quota 值执行。保留既有权限证明及角色规则。
- 套餐、商品和订单的列表、详情、编辑、购买及补单检查范围一致，不能仅筛列表而在详情或写入时漏检。已有功能优先扩展，不重复实现。
- 后台用户/Key/订单区分用户身份来源与 App 接入组合，代理用户订阅授予和购买均拒绝；历史 OAuth 订阅仍可审计，不转移到代理用户。一次性充值商品与周期订阅套餐分别标注。
- 更新子 App 框架及相关标准，默认优先推荐 Supabase 原生登录＋App 后端托管个人 AI Key＋管理员 PAT 管理/支付的代理模式，OAuth 作为按需选项。入口描述、接入步骤、身份/relay/支付/安全/Supabase 参考保持一致；代理模式不自动运行 OAuth provider bootstrap。明确凭据分工、支付矩阵、积分单位、范围及当前能力边界，不能将待开发接口写成已可调用。同步实际参考实现、starter 与 SDK/OpenAPI 的受影响公开契约。
- 若新增或修改 newapi-cli 行为，同步 CLI skill 与 App framework skill，并验证打包携带两者；否则不为本功能额外扩建 CLI。
- 不要求改造所有外部子产品；提供仓库内可运行的参考链路与独立代理接入说明，保留已有 OAuth 模式及历史 user_id，禁止按邮箱自动换绑或跨模式迁移资产。

## Testing Decisions

- 待用户确认的首选测试边界：公开 HTTP API 为后端主边界；浏览器代理分支为“Supabase 登录→积分→收银台→支付确认→AI→子 App 余额/订单”，OAuth 分支另行验证“授权登录→控制台钱包切换→本人余额/订阅”。两条分支用户独立，不用代理登录去验证 OAuth 资产。只断言用户可见结果、归属、账本差额与权限，避免测试私有 helper、CSS 全量快照或函数调用次数。
- 复用 OAuth App purchase 的跨 App 拒绝、余额付款、重复入账和合规门槛测试思路；复用用户 App quota 集成测试、token 路由测试、App wallet 与持久化任务结算测试。每个聚焦后端功能优先扩展一份合适的现有测试文件，必要时最多新增一份，不跨层散落重复断言。
- 前端在功能所属测试目录覆盖选择器、钱包和支付交互：普通用户选择、快速切换、乱序返回、账户切换、旧选择失效、空/错/加载、支付中换 App、键盘与移动布局。复用现有选择器及用户额度显示测试。
- 接入模式矩阵覆盖仅 OAuth、仅托管 Key、双模式、整体停用，以及旧 App 迁移默认值；关闭授权的 App 从顶部/钱包下拉消失、当前选择归位，但后台筛选仍可见且托管 Key 调用继续成功。隐藏配置字段不能通过直接请求绕过模式校验。
- 同 App、同邮箱的代理与 OAuth 用户保持不同 user_id，各自充值/调用互不影响；覆盖 Supabase 自动关联歧义和跨模式伪造。代理订阅的读取/购买/授予/抵扣全部拒绝，含双模式 App、余额不足且存在残留订阅的场景；OAuth 订阅正常。轮换各阶段失败、停用前下单后付款、比例 null/修改后的订单快照、旧 credits 客户端与新增字段分别回归。
- 以两用户、两 App、一个平台钱包的确定性夹具验证隔离；为用户、App、Key、订阅和支付方法显式初始化状态。新 Go 测试按项目规范使用 require/assert。
- 账本检查覆盖充值恰好一次、预扣与实际差额、失败退款、订阅资金来源、平台与其他 App 资金不变；流式中断及异步重试不得造成漏扣或双扣。数字边界覆盖非法比例、最小正数、非整除、安全整数上限和并发超额，不靠随机或压力循环证明正确。
- 所有影响数据库的 ticket 在关闭前，分别对真实 SQLite、MySQL、PostgreSQL 验证；schema 变更覆盖空库、最新发布版代表性数据升级、连续两次启动/迁移、数据与索引约束保留。共享日志路径还覆盖单独日志库；触及其查询时包括支持的 ClickHouse 路径。记录版本、实际命令及结果；缺失矩阵不得标已完成。
- 认证、凭据与代理授权修改实施前读取当时最新稳定 ASVS 及相关 OWASP Authentication、Session Management、Authorization、CSRF、Secrets Management 指南，记录采用版本与确实适用的要求 ID；本草稿不虚构已完成 OWASP 审计。
- 真实支付链路用测试商户或支付沙箱；未取得支付凭据时可以验证签名夹具与 HTTP 合同，但真实收银台验收保持未勾选。需要公网回调时使用临时 HTTPS tunnel，记录并在验收后清理临时配置。
- 每个切片交付自己的行为测试、适用构建与数据库验证，不把质量检查全部推到最后。最终组合验收汇总证据；每个实现分支按 merge-base 完整 diff 做项目要求的审计，修复真实 High/Medium 问题。
