## Problem Statement

代理 App 使用 Supabase 登录并在后端托管用户的 AI Key，希望在购买会员后允许指定时间内调用 AI，到期自动停止新请求。main 已新增配额管理，支持每个 Key 的自然日/周/月消费上限及允许星期，但没有绝对生效、失效时间，也没有为指定代理用户管理规则的接口。仅在客户端判断会员状态无法阻止直接调用网关。

需要区分三个概念：App 自己的会员订单和有效期、Key 的消费限制、真正支付 AI 消耗的钱包余额。现有规则只限制使用，不发放资金；同一模板的每个 Key 各有一份额度，不能视为用户共享会员余额。

## Solution

在现有配额规则中增加可选开始和结束时间，并在网关准入时强制检查。规则编辑、规则列表、Key 绑定和后台代理用户管理复用现有入口，让 App 后端使用管理员访问令牌为指定代理用户配置限时规则。

例如，App 后端验证自己系统内的会员付款成功后，为该代理用户的托管 Key 绑定一条启用的规则：北京时间 2026-12-01 00:00:00 生效，2027-01-01 00:00:00 到期，每个自然日最多消耗配置额度。到期即拒绝新请求；到期前已接收的任务仍按实际成本结算。App 必须另行保证对应 App 钱包有真实可用余额。

这支持 App 自建会员的时间和消费门槛；代理模式仍不支持 new-api 订阅，不改变 subscription_supported=false，也不开放其套餐购买、订阅发放或订阅扣费回退。两种登录模式继续使用独立用户，不建立关联。

## User Stories

1. As an App 管理员, I want 为配额规则设置开始时间, so that 会员权益可以预约生效。
2. As an App 管理员, I want 为配额规则设置结束时间, so that 到期后网关自动拒绝新调用。
3. As an App 管理员, I want 只设开始、只设结束或均不设置, so that 可以表达预约、限时和既有长期规则。
4. As an App 管理员, I want 精确到秒并看到明确时区, so that 不会误解“到期当天”的边界。
5. As an App 管理员, I want 时间有效期独立于星期限制和周期额度开关, so that 仅限时规则也能工作。
6. As an App 管理员, I want 知道修改模板会影响多少个 Key, so that 不会误改其他会员的有效期。
7. As an App 后端开发者, I want 使用管理员 PAT 管理指定代理用户的规则, so that Supabase 用户无需取得 new-api 控制台会话。
8. As an App 后端开发者, I want 规则归属由服务端从目标用户确定, so that 请求无法冒充其他用户或把管理员自己的模板绑定过去。
9. As an App 后端开发者, I want 在固定 App 范围内列出、创建、修改和删除目标用户规则, so that 可维护会员门槛。
10. As an App 后端开发者, I want 将目标用户自己的规则绑定到其同 App Key, so that 规则、Key、钱包归属一致。
11. As an App 后端开发者, I want 只读 PAT 无法编辑或绑定规则, so that 可按最小权限部署管理服务。
12. As an App 后端开发者, I want 查询规则有效期和服务端判定状态, so that 客户端不必自行推导会员是否过期。
13. As an App 用户, I want 在开始时刻即可使用、到结束时刻即停止新调用, so that 权益边界可预期。
14. As an App 用户, I want 在有效期内仍受星期和周期上限约束, so that 套餐描述与实际可用范围一致。
15. As an App 用户, I want 余额不足时收到准确错误, so that 不把配额限制误认为钱包充值。
16. As an App 用户, I want 到期前已接收的流式请求和异步任务可以正常完成, so that 已发生的 AI 工作不会因有效期变化丢失账务。
17. As an App 用户, I want 失败请求只退回实际预留的金额与规则用量, so that 不重复扣款或获赠余额。
18. As an App 管理员, I want 延长有效期不重置本周期已用额度, so that 续费操作不会重复赠送预算。
19. As an App 管理员, I want 知道自然月重置不等于购买后滚动一个月, so that 能准确设计会员商品。
20. As an App 管理员, I want 明确每个 Key 独立计额, so that 不将多 Key 额度宣传为一份共享用户额度。
21. As an App 管理员, I want 取消会员时使用到期或撤销 Key, so that 不会因停用规则反而移除限制。
22. As an App 管理员, I want 修改已到期规则后看到真实状态, so that 可处理补单和误操作而不伪造历史。
23. As an App 后端开发者, I want 已绑定规则的 Key 轮换被明确拒绝, so that 新 Token ID 不会悄悄得到一份新预算。
24. As an App 后端开发者, I want 重试规则更新不产生额外资金和用量清零, so that 网络失败不会影响账本。
25. As a 平台用户, I want 原有未设置时间的规则保持行为, so that 升级不影响现有调用。
26. As a 平台运维人员, I want 缓存存在时到期仍立即生效, so that 不依赖客户端或缓存 TTL 撤销权限。
27. As a 平台运维人员, I want 审计记录操作者、目标 App、用户、规则及结果, so that 可定位越权或错误配置且不记录可用凭据。
28. As a 后台管理员, I want 在已选 App 的代理用户 Key 管理内查看和配置规则, so that 不必在管理员自己的配额页面误操作。
29. As a 非中文用户, I want 时间字段、状态、校验和拒绝原因都有翻译, so that 可以正确理解有效期。
30. As a 维护者, I want SQLite、MySQL、PostgreSQL 新建及升级后重复启动都保留原规则和用量, so that 有效期功能可以安全交付。
31. As an App 后端开发者, I want 接入 skill 明确推荐代理模式并解释会员门槛与订阅资金的区别, so that 不会误接 new-api 订阅接口。
32. As an App 用户, I want 在途请求按准入时冻结的预算上限补扣, so that 后续规则改额或删除不会改变已接收工作的预算合同。
33. As an App 后端开发者, I want 安全取消未完成的 Key 轮换, so that 清理替换 Key 后可以继续为原 Key 绑定规则。
34. As an App 后端开发者, I want 取消后重放创建、提交或启用请求都不能恢复替换 Key, so that 已撤销的凭据不会再次可用。
35. As a 平台运维人员, I want 重启后保留预算快照和轮换取消终态, so that 恢复流程不会重算上限、卡住绑定或重新发放凭据。

## Implementation Decisions

- **复用模型。** 在现有 TokenQuotaRule 增加 nullable 的 valid_from、valid_until，数据库使用可空 bigint，API 使用 UTC Unix 秒整数或 null。不新建订阅、共享预算、排期实体。老行均为 null，保持原行为。
- **输入合同。** 两端可分别为空；非空必须为整数且在 1 至 253402300799（9999-12-31T23:59:59Z）之间，拒绝小数、字符串、负数、0 和溢出。两端非空时必须 valid_from < valid_until。允许过去时间用于立即过期和记录补单；不允许借用 -1 表示无限。创建缺省为 null；现有 PUT 按完整规则保存，缺省时间字段表示保持原值，显式 null 清空边界，避免旧客户端保存时无意解除有效期。
- **绝对边界。** 有效范围是 [valid_from, valid_until)，包含开始，不包含结束；空端无该方向限制。网关用服务端时钟，按请求在规则预留事务内取得的当前时间判定；不以浏览器时间、JWT 时间、任务完成时间代替。时间不依赖定时任务或一次性状态翻转。
- **时区。** 继续只支持 UTC 与 Asia/Shanghai。编辑时显示明确时区，将当地日期时间转换为绝对秒；切换显示时区保持同一绝对时刻，禁止暗中平移开始/结束。既有时区字段仍用于自然周期及星期判断；修改它对周期预算的影响必须明确提示。
- **准入组合。** 未绑定规则不增加限制；保持旧规则 enabled=false 表示“不执行该规则”的语义。启用后，无论是否开启周期额度或星期限制，都检查绝对有效期。绝对时间、允许星期、周期可用额度与既有 Key/用户/App 状态、Key 过期、模型/IP 权限及钱包条件共同生效，任何一项不能绕过另一项。免费请求、无限额 Key 和信任用户也必须通过启用规则的时间检查；保留现有受控 Playground 路径，不用其身份绕过代理 Key relay。
- **拒绝和展示。** 未生效、已到期的新 relay 返回 403，并提供稳定的 rule_not_started、rule_expired 原因，沿用规则准入错误和禁止重试语义，不自动换 Key、资金来源或 App。管理 DTO 返回 valid_from、valid_until、validity_status（disabled、scheduled、effective、expired），列表响应携带一次 server_time；Key 规则摘要同步字段。effective 只表示规则在时间上生效，不等于钱包充足、星期允许或本周期有额度，不用其伪造“可调用”承诺。错误给 AI 客户端的后端翻译与控制台七语言文案分别走既有机制。
- **账务。** 有效期不产生资金、不改变 quota/积分比例和价格。自然日/ISO 周/自然月预算保持既有时区及周期键；起始时间不成为重置锚点，结束时间不执行额度清零。仅修改时间、启停、额度上限和名称不删除或重建用量记录；续期延长同一规则不会重置同一周期用量。修改周期或时区可能选择不同周期键，不承诺预算连续，应提示并由 App 审慎管理，不能将此作为自动续费步骤。
- **在途工作。** 通过准入的请求保留原规则用量预留、用户/App 及资金来源。到期、进入新周期、修改规则、解绑或删除后，仍按原预留补充预扣、结算和退款，不重新按当前规则转移已发生用量。提交新的任务或新的独立请求必须重新准入。实际成本高于预估时记录实际消耗并阻止后续超额准入，不能裁剪实际账单来满足规则上限。
- **预算快照与持久化。** 扩展现有规则预留合同，保留 RuleID、UsageID、Amount，并新增 snapshot_version=1、quota_limit_enabled、quota_limit。准入事务在锁定规则并成功预留时冻结是否限额及安全整数上限；限额请求绑定原 UsageID，该 ID 固定对应原 Token、规则和自然周期，不按当前时间重新定位。时间规则本身不需要用于后续准入的第二份快照。同步请求持有该快照；异步任务在发送上游前将快照与原用户/App、资金来源一起持久化到既有任务私有数据，任务创建失败按原预留回滚，恢复时不得从客户端或当前规则重新生成快照。
- **补扣、改额与旧预留。** 已接受请求的补充预扣使用快照上限对原用量行做原子条件更新，不再查询规则是否存在、是否启用或当前额度；成功后同步累计 Amount。共享同一用量行的预留都检查该行累计已用值，不能各自创建新预算。规则改额只影响之后的独立准入：例如原上限100、已预留40后降为50，原请求仍可在原行累计不超过100时补预留，新请求按50判断；旧请求继续补扣可能使累计用量超过新上限，此时新请求保持拒绝。准入时未限额的请求不因后续启用上限而补建预算行；其后续工作继续按原钱包/Key资金合同执行。结算和退款依赖原 UsageID 与实际预留，记录真实成本而不按快照裁剪账单。无快照的历史预留继续允许原 UsageID 的结算和退款；需要正向补预扣时明确拒绝并返回 reservation_snapshot_unavailable，不能猜测原上限或改成无限额，发送上游前按既有失败路径结束并退还未消费预留。该兼容限制须在升级说明和验收中明确。
- **用户与模板。** 规则继续属于用户，同一规则在多 Key 上仍分别计额。代理用户具有不可变 owner App，因此规则的 App 归属从该用户推导，不增加可独立改写的 app_id。每位会员需要独立有效期时，为目标代理用户创建独立规则；不跨用户复用一条管理员模板。编辑多 Key 绑定模板前展示绑定数量及共同受影响提示。
- **代理管理接口。** 在既有 app-proxy 目标用户管理接口族增加 GET/POST quota-rules、PUT/DELETE quota-rules/:rule_id，以及 PUT keys/:token_id/quota-rule，沿用必填 app_id 查询参数及绑定请求的 rule_id（0 明确解绑）。服务端验证管理员身份、PAT 权限、目标是代理用户、owner App 与请求 App 一致、规则属于目标用户、Key 也属于目标用户和 App；禁止依赖前端筛选。读用 api_key:read，写和绑定用 api_key:write，同时保留管理员/Casbin 检查；普通用户 PAT 不因拥有 scope 就获得指定用户权限。
- **旧入口和权限。** 现有 self 配额规则 API 继续只管理调用者本人，不允许传 user_id 冒充代理用户。代理管理接口返回目标用户规则，不能误用 PAT 持有者的规则。未知字段明确拒绝；路径、请求与持久化归属冲突时拒绝。App 禁用或代理模式关闭后禁止创建、修改和绑定；允许有权管理员读取记录、解绑、撤销 Key 及取消未完成轮换等收尾操作，仍需校验目标归属。不扩大 PAT 到任意 App 的隐式访问范围；App 后端固定自己的 App 参数。
- **托管 Key 的安全绑定。** 代理首次创建托管 Key 时支持可选 quota_rule_id，由服务端在同一事务校验目标规则并创建绑定；没有绑定前不向 App 返回一个可调用的临时无约束 Key。幂等创建指纹包含规则 ID，重试保持原绑定、不清零用量。现有 Key 用专门绑定操作；通用策略更新不能静默修改绑定。SDK/OpenAPI 及 BFF 同步严格字段合同；旧客户端省略该字段保持原行为。
- **轮换边界。** 本轮 rebase 的兼容保护对绑定任何规则（即使停用）的 Key 拒绝阶段轮换，并在提交阶段重新锁定原 Key 检查。未来有效期功能继续此限制，不能通过复制 QuotaRuleId 到新 Token ID 声称预算连续。未来代理绑定接口在同一事务拒绝仍存在 pending 轮换的原 Key；阶段轮换已有新 Key 时，必须先完成下面的取消操作才能绑定。创建轮换、绑定、提交及取消须围绕同一原 Token 串行化，并采用一致的锁顺序，防止“检查无轮换后又生成替换 Key”的竞争；同一原 Key 存在多个历史阶段操作时，所有 pending 操作都须结束。解除规则再轮换不属于预算连续能力。
- **轮换取消合同。** 保留现有 Committed 字段，在操作记录增加 Cancelled 布尔值，旧行默认为 false；两者均 false 为 pending，仅 Committed 为 true 是 committed，仅 Cancelled 为 true 是 cancelled，禁止两者同时为 true。增加 POST keys/:token_id/cancel-rotation，路径 Token 为替换 Key，沿用目标代理用户、必填 app_id、管理员权限及 api_key:write 校验；只接受确实存在且原 Key/替换 Key 均属于该目标用户和 App 的轮换。取消在一个事务中锁定对应操作和两把 Key，将替换 Key 设为禁用并标记 Cancelled，原 Key 的状态、绑定和用量保持不变；缓存失效按既有凭据撤销机制执行，成功返回操作状态而不返回凭据。
- **取消终态、重试和恢复。** 重复取消同一 cancelled 操作返回成功；取消 committed 操作返回409 operation_conflict，不撤销已完成切换的 Key。提交 cancelled 操作、使用原幂等键重新创建 cancelled 操作、通过 Key 策略更新重新启用 cancelled 替换 Key，均返回409 rotation_cancelled，不能复活或再次返回其秘密；需要轮换时使用新的操作幂等键并重新校验原 Key。人工禁用替换 Key 不代表操作已取消，仍可调用取消接口完成终态。提交与取消竞争时只能一个终态成功；取消先成功则原 Key 不被随后提交撤销，提交先成功则取消不再改动两把 Key。取消事务失败不得留下半完成状态，重试可恢复；重启后保留终态。取消生效后，所有凭据入口均拒绝替换 Key，即使命中旧缓存；已接收工作继续按原账务预留结算，绑定检查忽略 cancelled/committed 操作但保留历史记录。SDK/OpenAPI、BFF 管理允许列表和后台 Key 面板同步此合同，UI 在取消成功后刷新轮换状态与绑定入口。
- **UI。** 扩展既有规则编辑 Dialog，加入可空开始/结束日期时间、时区、端点含义与就地校验；列表及 Key 规则摘要显示时间范围和上述时间状态。后台复用 App 筛选、代理用户 Key 面板及规则编辑/绑定组合，查询缓存同时包含目标用户和 App，切换后不显示另一用户规则。优先复用项目日期时间和确认组件；七语言齐全，Intl locale 经项目转换。停用或解绑必须明确提示“移除限制，不是停用 Key”；取消会员推荐设置结束时间并保持规则启用，或撤销对应 Key。
- **会员生命周期分工。** App 验证自己的会员付款后保存订单/权益，并设置或延长目标规则；网关不根据这些日期创建 new-api 订阅。续期金额、支付重放/乱序、退款、取消、到期资金处置由 App 已验证的业务流程处理。修改规则本身不得充值、扣款或自动退款；退款也不能只解绑规则。若 App 需要权益和资金发放的原子保证，必须另立合同，不通过两个非原子请求宣称已支持。
- **审计与接入指导。** 记录操作者、App、目标用户、规则/Key ID、有效期变更和结果；审计不记录 PAT、AI Key、session/JWT 或原始支付凭据。接入 skill、参考 App 和 API 文档解释默认代理模式、启用规则、钱包资金前提、自然周期、多 Key 及取消操作；不要把代理订阅能力开关改成 true。认证相关实现按 OWASP Authentication、Session Management 及 ASVS 5.0.0 适用控制复核；具体适用要求和验证结果在实现交付时记录，不以本规格声称合规。

## Testing Decisions

用户于 2026-11-19 确认：优先复用公开管理 API 和 AI relay 作为测试边界，覆盖有效期、配额预留/结算/退款与越权，再用浏览器验证日期配置和到期状态。测试断言外部行为与账本结果，不断言内部字段选择、文件布局或私有常量。

- **API/relay 主边界。** 扩展既有规则授权审计、App 代理数据库矩阵及统一计费矩阵，不按每一层新增重复测试。原有自然周期/验证表驱动测试可补时间边界；使用可控制的时间样本，不用 sleep 等到期。
- **时间表。** 覆盖未设置、单端设置、开始前一秒、开始同秒、结束前一秒、结束同秒，UTC 与北京时间同一时刻、跨日/月/年，已过去范围、非法类型/数值/顺序。有效期独立于周期额度/星期开关；老客户端 PUT 缺省保持边界，显式 null 才清空。
- **入口绕过。** 有余额、无限 Key、信任旁路、免费模型、流式/非流式及异步提交在到期后均不能新准入；星期拒绝、周期耗尽、Key 自身过期、App/用户关闭仍生效。命中缓存也在边界准确拒绝；不请求真实上游即可验证网关拒绝，真实成功扣费仍需测试上游。
- **账务合同。** 准入前拒绝不残留规则/Key/钱包预扣；到期前接收的同步、流式、异步任务在到期后正确结算；失败退款、重复回调按既有幂等约束执行，不能重复退。验证规则编辑/解绑/删除、跨周期和重启后的持久化预留仍归原用量与 App 钱包。原上限100、预留40后降为50，旧请求补30成功且原行累计70，新请求拒绝；原上限100后改为200，旧请求仍不能补至超过100。删除规则后旧请求仍可在冻结上限内补扣；同原行并发补扣只能容纳剩余额度，不产生独立新行。补充预扣超限不改规则/Key/钱包余额，失败路径按已发生工作精确退款。覆盖无限额快照、任务快照持久化失败、重启后补扣、无快照历史任务的补扣拒绝及正常结算/退款；未获得补扣许可时不发送新的上游请求。延长结束时间不清零、同模板两 Key 分别计额、不回退平台或 new-api 订阅资金。
- **授权及轮换合同。** 无认证、无管理员角色、只读 scope、跨用户/跨 App/错误来源、伪造 owner、混合路径和请求参数、禁用 App 及已撤销 PAT 均覆盖。首次创建和绑定原子成功/失败；幂等重试不改规则或生成新预算。绑定规则的阶段轮换与提交拒绝；pending 轮换阻止绑定，取消后同一原 Key 可绑定，多个 pending 操作须逐一结束。覆盖取消重试、人工禁用后取消、取消后提交/幂等创建/重新启用拒绝、committed 取消拒绝、取消事务失败回滚及重启恢复。对提交与取消、创建与绑定做有确定次序的并发回归，断言仅一个有效结果、缓存中的替换 Key 不可用、原 Key 状态及预算不被取消误改。App 关闭后有权管理员仍能取消，scope 或归属不符始终拒绝。审计包含取消目标与结果并排除可用秘密。
- **三数据库。** 实际 SQLite、MySQL、PostgreSQL 执行新建和代表性已发布数据库升级，各连续迁移两次。验证 nullable 时间、Cancelled 默认 false 及旧 committed/pending 状态保留、旧规则默认、旧用量/索引/唯一约束保留、边界查询、事务与规则绑定竞争。验证任务私有数据中新增快照的保存/读取及旧数据兼容。涉及独立日志库路径时一起验证；记录版本、命令、结果，缺引擎时不得宣称完成。
- **浏览器。** 扩展既有配额规则和代理用户 UI 测试；实际浏览器设置、清空、保存并重开时间范围，确认时区切换不改变绝对时刻、错误可读、到期状态刷新、多绑定影响提示、键盘操作和 App/用户切换隔离。完成七语言键与占位符检查、类型检查和构建；客户端展示不能替代 relay 时间校验。
- **验收完成条件。** 上述 API、relay、数据库及浏览器合同均有真实执行证据；复核相对分支基线的全部差异并修复 High/Medium 缺陷。缺真实支付/AI 沙箱时分别列为未验收，不用夹具余额或模拟付款宣称完整会员支付闭环。
