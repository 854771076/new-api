- 负载:**10 个仿真 coding 客户端 × 每客户端 50 请求 = 500 请求/配置**,共享 1 把 API key

- 指标:成功率、429 数、成功请求延迟分位、>10s 占比、排队深度峰值、per-client 成功数(公平性)

## 分析

1. **A(无队列,C=3)不可用**:22.8% 请求被直接拒绝,且**公平性崩坏**——运气好的客户端完成 43/50,运气差的只有 30/50。交互式 coding 场景下 1/5 的操作"凭空失败",用户会归咎于工具而不是网关。
2. **B(小队列救回大部分)**:94.6%,但队列常满(峰值 4=上限),仍有 5.4% 429;尾部延迟翻倍(p95 3.0s)。10 客户端已经压到这套参数的天花板。
3. **C 是甜点**:零 429、完全公平(50/50)、p95 1.78s、97% 请求 2s 内返回。峰值排队 5,离 Q=10 上限还有一倍余量——还能再吸收约一倍的突发。
4. **D(过度配置)无收益反有害**:成功率同为 100%,但 max 从 3.4s 涨到 5.9s——活跃上限放到 8 后,上游偶发被更深的并发压出长尾;且占用上游容量多 60%。
5. **E(浅队列+短等待)验证了方向**:Q=1×C 太浅、等 3s 太紧,队列一满就漏 429,尾部(max 7.4s)反而比 C 差。**深度按 2×C、等待 5s 是必要的**,不是保守。

## 推荐配置(10 个 coding 客户端共享一把 key)

| 参数 | 值 | 依据 |
|---|---|---|
| key 并发上限 C | **5** | 平均负载实测 ≈2.5 槽,C=5 留 2× 余量;3 不够(77–95%),8 无增益 |
| queue_depth_ratio | **2** | E 组证明 1×C 会漏;2×C 吸收全部突发 |
| queue_depth_cap | **10** | Q=min(2×5,10)=10,峰值 5 仍有一倍余量 |
| queue_max_wait_seconds | **5** | E 组证明 3s 偏紧;5s 下零超时,最慢 3.4s,coding 客户端(HTTP 超时 ≥60s)无感 |

扩展估算(线性外推):每增加 10 个 coding 客户端 ≈ 增加 2.5 个并发槽需求,按 C=需求×2 取整配置;客户端数翻倍到 20 时同模型推 C=10、Q=20、等 5s。

## 配置入口

- C:API Keys 页 → 该 key 抽屉 →「并发请求数上限」
- Q/等待:/concurrency 页 →「Bounded wait queue」卡片(Depth ratio / Depth cap / Max wait),保存即生效
