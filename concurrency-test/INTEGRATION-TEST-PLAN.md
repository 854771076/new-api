# 集成测试方案:并发上限 + 有界等待队列 + 429 降级(配置经验产出)

> 状态:待执行(配置齐即可跑)。唯一配置源:`concurrency-test/config.json`。
> 决策来源:2026-10-15 与测试负责人的 11 问对齐,全部推荐已获同意。

## Problem Statement

生产环境即将部署「并发上限 + 有界等待队列 + 429 降级」这套机制,但没有可信的配置经验:队列深度(ratio/cap)、等待时长(max_wait)、三级并发上限(key/user/channel)该配多少,没有任何数据支撑。已经观察到一个初步规律——队列长、并发低时 429 变少;服务集群 1 分钟处理量与队列长度接近时,客户端体验良好——但这是单次非专业测试的感性结论,没有对照、没有边界、没有容灾场景,不能直接指导生产配置。生产是多节点部署,而队列是 per-node 的,配置经验值如何随节点数折算也完全未知。

## Solution

一套由 `config.json` 驱动的黑盒集成测试:10 个客户端 × 各 50 个不同长度任务(四档长度分布),阶梯升压扫出「到达率 ↔ 队列长度 ↔ 1min 吞吐 ↔ 429 率 ↔ 体验」的拐点;在单节点主矩阵上完成队列参数扫描与渠道/key 拓扑对照,在双节点专项上完成容灾降级注入(Redis 宕机、节点掉线、热调配置)。最终交付三样东西:**参数查表**(给当下用)、**折算公式**(给换规模时用)、**生产 checklist**(给值班用,含告警阈值)。

## User Stories

1. 作为测试执行者,我想只改 `config.json` 就能配置全部测试参数(且有可运行的默认值),以便不改代码即可重复执行。
2. 作为测试执行者,我想让 10 个客户端各发 50 个任务、长度按四档(500/1000/2000/4000 词)分布,以便负载形态贴近真实混合流量。
3. 作为测试执行者,我想让客户端对半分成「脆弱画像」(429 不重试,记为失败)与「健壮画像」(遵循 Retry-After 退避重试),以便一轮同时拿到两种客户端体验。
4. 作为测试执行者,我想按阶梯(1→2→4→6→8→12 req/s,每档 60s)升压并在每轮开头突发 2.2 任务建队列,以便扫出拐点而不是拿到单点。
5. 作为测试执行者,我想自动逐档切换队列 4 参数(0/2/8/3s → 4/128/10s → 16/64/10s → 64/128/20s)并复跑阶梯,以便产出 Q 参数扫描矩阵。
6. 作为测试执行者,我想自动布置单渠道与 3 渠道(同质上游)两种对照场景,以便把 429 归因收敛到闸门本身而非上游差异。
7. 作为测试执行者,我想跑「10 个独立 key(limit=3)」与「10 客户端共享 1 key(limit=3)」两种拓扑对照,以便量化全局抢位对公平性的影响。
8. 作为测试执行者,我想主矩阵用可控假上游(固定延迟+抖动)、收尾用真实推理集群跑 1-2 轮,以便兼顾可重复性与真实校验。
9. 作为测试执行者,我想每个负载档位同时轮询快照端点(3s)采集成-flight/queued/rejections,以便服务端状态与客户端体验逐时刻对齐。
10. 作为测试执行者,我想每轮把客户端明细落成 jsonl、把汇总落成 markdown 报告,以便复盘与留证。
11. 作为指标对账者,我想把客户端侧 429 计数与服务端 rejections 计数(取轮间差值)逐档对账,以便验证「客户端看到的 = 服务端算到的」这条等式。
12. 作为指标对账者,我想从日志成功行(按分钟窗口计数)直接算出 1min 处理量,以便验证你的「吞吐 ≈ 队列长」经验假设。
13. 作为指标对账者,我想同时开启错误日志,以便把渠道路径 429 也落库做第三方对账。
14. 作为体验评估者,我想拿到每档的完成率、端到端 p50/p95、首次 429 率、重试后最终失败率四项指标,以便判定该档体验是否合格。
15. 作为体验评估者,我想用「无队列基线轮」的 p95 作参照(K=3 倍),以便在不加服务端埋点的前提下近似排队成本。
16. 作为体验评估者,我想按客户端分别统计体验,以便发现队列对某个客户端的系统性不公。
17. 作为容灾测试者,我想在打流中杀掉 Redis,以便观察 fail-open、Degraded 徽标三态、降级窗口合并计数与恢复回溯。
18. 作为容灾测试者,我想在双节点拓扑中杀掉一个网关节点,以便观察租约接管、在途计数归零与幸存节点的队列语义(排队位 = N×Q)。
19. 作为容灾测试者,我想在负载中途热改队列参数,以便测量跨节点传播延迟(预期 ≤60s 轮询)与生效行为。
20. 作为容灾测试者,我想让租约 TTL 用 30s 覆盖,以便掉线接管在测试窗口内可见。
21. 作为容灾测试者,我想把 auto-ban 恢复测试作为可选轮(默认关),以便按时间预算裁剪。
22. 作为运维配置者,我想得到一张「Q 参数 × 到达率 → 429 率/p95」查表,以便直接给生产填值。
23. 作为运维配置者,我想得到 Q* ≈ 到达率 × 目标等待 的折算公式与多节点口径(每节点 Q,总等待位 N×Q),以便生产扩节点时重新推导。
24. 作为运维配置者,我想得到生产 checklist(含 queued 峰值、429 率、Degraded 三态的告警阈值),以便值班直接采用。
25. 作为运维配置者,我想配置项在 UI 上都能手动改(队列 4 项、三级 limit),以便按 checklist 回改生产。
26. 作为客户端集成方,我想验证 429 响应恒带 `Retry-After: 1` 且错误形为 `concurrency_exceeded`,以便按契约实现退避重试。
27. 作为客户端集成方,我想确认 key 来源与 channel 来源 429 对外同形,以便不依赖响应体做分支。
28. 作为平台开发,我想整个方案零新增产品代码缝(全部黑盒),以便测试不反向污染实现。
29. 作为平台开发,我想复用已有测试脚本的采样与断言模式,以便维护成本最低。
30. 作为报告阅读者,我想每轮报告都带执行环境指纹(镜像 tag、config 快照、起止时间),以便结论可复现。
31. 作为项目负责人,我想 `config.json` 中未填的 `_todo` 项在执行前被显式检查并列出,以便不会拿默认值冒充生产输入。
32. 作为项目负责人,我想全部矩阵在预算(默认 6h,可过夜)内跑完,以便当天拿到结论。

## Implementation Decisions

**拓扑与场景(来自 Q1-Q5,全部已批准)**

- 主矩阵单节点(镜像容器 + db 副本 + 宿主 Redis);容灾专项双节点——现有 compose 无双网关拓扑,需在测试项目内新增一个双网关 compose(两网关各持 SQLite 副本、共享宿主 Redis,避开 SQLite 跨容器共享),双网关读写日志各归各,观测以客户端口径为准。
- key 拓扑:10 独立 key(各 limit=3)为主轮,共享单 key(limit=3)为对照轮,两轮都跑。
- 渠道拓扑:单渠道与 3 渠道两场景对照,渠道上游同质(克隆同一上游),channel limit=3;异质延迟不进本方案。
- 上游:主矩阵走可控假上游(delay-proxy 需参数化上游地址,当前硬编码,属测试代码改动);收尾轮切真实集群,预算由 config 填写。
- 降级分层:主矩阵含 ①队列削峰 429 ③上游 429 换渠道;专项轮含 ②Redis fail-open ⑥节点掉线 ⑤热调配置;④auto-ban 默认关,config 可开。

**负载与画像(来自 Q6-Q7)**

- 每轮 10 客户端 × 50 任务,客户端对半分双画像(5 脆弱/5 健壮),画像在所有轮共用,不单独成轮。
- 负载形状:每轮开头 20% 齐发建队列,随后阶梯升压(1→2→4→6→8→12 req/s,每档 60s);队列扫参轮对每一档 queueSweep 配置复跑同一阶梯。
- 任务长度四档沿用既有分布(500/1000/2000/4000 词,32/20/10/5 配比)。

**指标与观测口径(来自 Q8/Q10/Q11)**

- 体验指标四项:完成率、端到端 p50/p95、首次 429 率、重试后最终失败率;合格线 = 完成率 ≥99% 且 p95 ≤ K×无队列基线(K=3,config 可覆盖绝对值)。
- 429 率以客户端统计为权威;服务端 snapshot `rejections` 取轮间差值交叉验证;错误日志开启后渠道路径 429 落库做第三方对账。处理量 = 成功日志按分钟窗口计数。
- 排队成本用「有队列轮 vs 无队列基线」p95 差值近似,**本轮不加服务端埋点**;快照 3s 轮询,history 10s 采样仅作留证补充。
- 队列等待时长无服务端直出字段、429 响应 key/channel 同形——两者都是既有契约,测试不得依赖响应体区分来源,归因靠脚本侧记账与内部日志。

**参数与生效语义(来自事实探查)**

- 队列 4 参数全热生效(写入节点即时,跨节点 ≤60s 轮询);token/user limit 经 Redis 即时,channel limit 跨节点 ≤60s——热调轮的预期值以此为准。
- Q = min(ratio×C, cap) 按 scope 自身 limit 算;C=3/key 时各档实际 Q 在报告中列出。
- 多节点口径:排队位 = N×Q(per-node),活跃上限全局(Redis ZSET);公式与查表按「每节点 Q」给。
- 租约 TTL、熔断 cooldown 用 env 覆盖(每次 trip/续约时读,改值仍需重启容器,视为部署动作而非热配置)。

**交付物**

- 每轮 jsonl 明细 + 汇总 markdown 报告(沿用既有 REPORT 惯例,带镜像 tag 与 config 快照指纹);最终一份综合报告含查表、公式、生产 checklist 三节。

## Testing Decisions

- **好的测试只断言外部行为**:本方案全部通过 4 个黑盒缝验收,不断言内部结构。
- **测试缝(Seams,全部为既有缝,零新增)**:
  1. 客户端中继缝:`POST /v1/chat/completions`(Bearer key)——唯一负载入口,429/Retry-After/时延都在这里观测。
  2. 管理观测缝:并发快照/历史/路由健康三个只读端点 + 队列参数写入端点 + token/user/channel 管理端点(布置拓扑)。
  3. 日志账本缝:成功/错误日志查询(按分钟窗口算处理量、对账 429)。
  4. 上游缝:delay-proxy 单点替换(延迟注入的唯一位置)。
- **被测对象**:整机网关(镜像容器),双节点专项为两容器 + 共享 Redis。
- **前置校验**:执行前读 `config.json` 并打印 `_todo` 清单,任何未填项以警告阻断「真实上游轮」而非全量。
- **优先测试的断言**:客户端 429 计数 ≡ 服务端 rejections 差值;无泄漏(压后 queued=0 且 in-flight=0,复用 S4 断言);Redis 被杀后 degraded.active=true 且快照仍 200、恢复后归位而 lastDegradedAt 保留;热改队列跨节点 ≤60s 生效;合格线四指标。
- **既有先例**:队列场景套件(S1-S5 的 429 分类与耗时窗断言)、退避重试脚本(Retry-After 遵从)、负载均衡报告的 3s 采样与日志归因模式、镜像验收轮的快照轮询对账——新 harness 以这些为模板,不另起炉灶。

## Out of Scope

- 不改任何产品代码、不加服务端埋点(排队成本用基线差值近似)。
- Sentinel 故障切换 soak(已有 runbook 挂账,不并入本方案)。
- auto-ban 恢复的默认验证(config 可开的可选轮)。
- EWMA 选路质量、429 不单跳(RTE-02)、上游 429 透传——已有专项报告覆盖。
- UI 视觉/交互回归(一屏页已另行验收)。
- MySQL/PG 三库矩阵(本方案沿用 SQLite 副本 + Redis)。
- 生产环境实际执行与真实凭据管理(真实上游预算由负责人在 config 填)。
- 异质渠道延迟、多租户/订阅、计费正确性(不触碰计费)。

## Further Notes

- 你的原始经验「1min 处理量 ≈ 队列长度时体验良好」将在 M5 扫描中被显式检验:以每档到达率、queued 均值/峰值、1min 处理量、p95 四元组拟合,若拐点吻合则公式成立,若不吻合按实测残差修正后写入报告。
- Little's law 是拟合起点(W ≈ L/μ),查表给绝对值,公式给推导,checklist 给告警阈值——三者互为冗余,配置变了也不会失效。
- 需要你逐项配置的只有 `config.json` 里 4 个 `_todo`(真实上游预算、时间墙、绝对 p95 阈值可选、生产规模);其余默认值即可开跑。
