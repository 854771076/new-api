1. **429 对账等式 9/9 轮精确成立**(Σ客户端429 ≡ Δ服务端 rejections)——观测口径可信,生产监控可直接复用。

3. **你的经验假设成立,但要修正半句**:队列的存在把首击 429 从 14.4% 打到 0%;但「队列更长 → 429 更少」在 **cap ≥ 自然峰值队列(本负载形状 ≈50)之后完全饱和**——cap=128 与 cap=128×激进档结果无差异,p95 也几乎不变。真正决定体验的是三件事:**① 有无队列 ② cap 是否截断突发 ③ maxWait 是否覆盖等待**;稳态队列其实很浅(meanQueued≈0.8),只有突发瞬间冲到 40-50。

## 折算公式(给换规模用)

- **自然峰值队列** ≈ 突发任务数 ×(1 − 单key limit / 每key并发在飞)≈ burst 中每 key 压入 20、通过 3 → 峰值 ≈ 10-15/key(本负载实测全局限 ~50)。
- **配置规则**:`Q = min(ratio×C, cap)` 应 ≥ 单 key 突发压入量的 2 倍;`cap ≥ 2×预期峰值`,`ratio ≥ 4`(保证 Q 不被 cap 截断)。
- **多节点(推导,未实测——D2 待跑)**:排队位 per-node,总可等待 = **N×Q**;活跃上限全局(Redis ZSET)。扩 N 节点时**每节点 Q 不用减**,但压测得到的「全局限流点」按全局 C 核算;告警阈值按单节点 queued 口径。
- Little's law 校验:峰值 L≈45、服务 μ≈13/s、W≈3.4s ≈ L/μ ✓(与 p95−基线同量级)。
